# 断言挑战（隔离源码变异与黑盒注入）

定位：回答"断言本身是否真的会报警"——不是再跑一条用例，而是制造一个**确定的语义变化**或**确定的故障**，检验目标断言能否捕获。本文只规定判定纪律与记分口径；执行编排与预算见 `adversarial-testing.md`，判据登记见 `oracle-contract.md`，结果记录结构见 `schemas/challenge-results.schema.json`。

**能力声明：本文全部执行器与浏览器拦截适配器仅为接口约定，能力待探测，未实测。** 实际可用性以当次会话能力探测（见 `adversarial-testing.md`）为准；通道不支持时不得虚构执行，按缺口分类记入"暂不支持"并附恢复条件。

## A 节：隔离源码变异

以受控修改源码的方式制造语义变化，检验断言是否"杀掉"该变异。纪律：

1. **只在隔离副本执行**：变异前先复制目标代码为隔离副本（工作树快照或独立检出），一切变异、构建、运行都发生在副本内；生产工作树与用户文件不变。
2. **基线必须先绿**：副本在未变异状态下先跑目标断言集合，必须全绿才开始变异；基线不绿不得发起变异，结果记 `baseline_green=false` 并终止该变异。
3. **单变异逐个跑**：每个变异单独构建、单独运行，一个变异的失败不得污染下一个；变异集合在执行前冻结（登记清单），执行中不得增删。
4. **结果只认四态加一**：
   - `killed`：目标断言**捕获了语义变化**（断言失败且失败原因可归因到该变异）才计 killed；构建失败、断言超时无关失败不算；
   - `invalid_build`（I）：变异导致副本构建失败，记 I；
   - `equivalent`（E）：已证明该变异与原语义等价（如注释级变化），记 E；**等价证明归人工裁定**，工具不得自动判 E；
   - `tool_error`（U）：驱动/工具异常导致未裁定，单列 U；U **不计完成也不计存活**，只计"未裁定"；
   - 其余为 `survived`：变异后断言仍全绿，变异存活。
5. **分母与分数**：分母 G=冻结集合中**基线适用**的变异数（不适用的变异不入集合）。完整分数 = K/(G−I−E)，**仅当 U=0** 时给出；U>0 时该轮标"**未完成**"，不得给出完整分数，可另报保守下界 K/(G−I−E) 并注明"**固定分母的保守检出下界**"（未裁定项按未检出计）。分母为零时输出 "NA"，不输出 100%。
6. **恢复核验**：每个变异跑完必须校验和比对并还原隔离副本，`restore_verified=true` 才算闭环；未核验的变异结果单列待复核。生产工作树在全程前后各做一次校验和比对留证。
7. 汇总口径见 `scripts/challenge_summary.py`（G/I/E/K/survived/U 分列），记录字段见 `schemas/challenge-results.schema.json`（`kind=source_mutation`，`injected` 恒为 true）。

## B 节：黑盒断言挑战

不触碰源码，通过外部手段制造确定故障，检验断言与候选归因。**前置：必须先探测当次浏览器通道是否支持请求拦截/路由替换**（见 `browser-connection.md` 与 `adversarial-testing.md` 能力探测）；探测不通过时，退回既有 `blind_eval` 夹具路径（`docs/evals-baseline/detection-protocol.md`），不得强行注入。

1. **成对采集**：每个注入点先采集**健康对照**（无注入，断言应静默）与**已知故障**（注入，断言应报警）成对样本；没有健康对照的注入结果不判 killed。
2. **三类黑盒替代，分账记录**：
   - **本地代理替换响应**：代理层改写响应（如注入 500），只记**客户端表现**（无限加载、错误提示、重试行为），不记后端自然缺陷；
   - **受控契约 stub 已知错误响应**：stub 返回契约中明确列出的错误形态，检验断言是否按契约报警；
   - **隔离环境合法状态/时序扰动**：在隔离环境中制造合法但异常的状态或时序（慢响应、重复回调），检验端到端不变量。
3. **一律不称"源码变异杀伤率"**：黑盒挑战与源码变异是两本账，禁止把黑盒检出混入 K/(G−I−E) 口径；汇总按 `kind` 分账输出（`scripts/challenge_summary.py`）。
4. **注入判别格**：
   - 注入故障与自然故障必须分开记录，`injected` 标志必填（true=人工注入，false=自然暴露）；
   - 注入产生的故障表现**不得记为产品缺陷**；客户端对注入故障的表现（如无限加载）可依据明确恢复规则记**客户端候选**；
   - **撤销注入后必须复测恢复健康对照**：`restore_verified=true` 表示撤除注入后复测恢复正常；未复测或未恢复的注入检出按"归因存疑/误报"单列，待人工裁定；
   - `injected=false` 且断言报警的，记**自然缺陷候选**（才可进入 `finding-triage.md` 候选流程）；把注入故障误报成产品缺陷的，按 `finding-triage.md` 复核口径记误报，不计检出。
5. 记录字段见 `schemas/challenge-results.schema.json`（`kind=black_box_injection`）；通道能力缺口按四分类登记，标注"能力待探测，未实测"。

## 与既有流程的衔接

- 挑战结果（CHL-）是对抗事件（EVT-）的补充证据来源：killed/survived 不直接等于缺陷有无，候选定性仍走 `finding-triage.md` 状态机；
- 黑盒注入的执行编排、扰动启停与副作用核对仍受 `adversarial-testing.md` 约束；
- 计分工具：`scripts/challenge_summary.py`（分账汇总）、`scripts/finding_summary.py`（候选聚类与复现率），两者只读输入、不替代门禁。
