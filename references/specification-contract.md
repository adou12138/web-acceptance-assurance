# 新需求与验收规格契约

## 稳定标识与追溯

使用 REQ（需求）、FUNC（功能）、FP（功能点）、AC（验收条件）、SCN（业务场景）、PATH（场景路径）、TC（执行用例）、RUN（运行）、BUG（缺陷）、EXP（探索）稳定 ID。名称用于展示，引用使用 ID，名称调整不改变标识。本次不需要的类型可省略，但不能把不同需求共用一个含糊断言。结构化文件的必填关系与工具规则见 `references/case-data-contract.md`，采用文件化数据时以该契约为准。

每条需求必须能正向定位到 AC、场景、用例和执行证据，或明确列出缺失项；每条用例也能反向定位到需求、风险或历史缺陷，防止孤立测试。独立数据组合生成不同 TC；套件复用同一 TC，运行记录用 RUN 与 attempt 区别。新增和废弃保留版本依据。

## 需求记录必填项

REQ ID、原文/来源定位、本次新增或修改点、旧行为（可知时）、新行为、业务角色、触发入口/开关、输入输出、关联模块、规则确认状态、待澄清问题。

明确区分：已确认规则、可撤回的暂定假设、阻塞判定的歧义。逐条检查完整、明确、一致、可验证及新旧兼容性，核对默认值、角色权限、合法/非法状态、边界、时间精度、失败恢复及空/加载/错误态。需求与原型矛盾时记录冲突，向业务确认；实现与需求不一致是待验证现象，不能反过来修改标准以适配实现。口头需求也可形成来源记录，不强制存在 PRD 文件。

问题类型分账：需求缺失/冲突记录缺失规则与受影响REQ/AC/TC，不直接计为产品BUG；实现缺陷需已确认判据和真实失败证据；主观体验建议标明启发式依据、观察任务和预期收益，不伪造业务硬规则或用户研究结论。已有客观任务阻断或确认设计/无障碍要求时可据实判实现问题，不能将全部界面问题泛化为审美偏好。缺规则只暂停依赖该规则的判定，其余明确部分继续。

## 验收条件必填项

AC ID、REQ ID、是否必选及理由、适用角色/状态/数据、具体业务结果、观测入口、通过标准、确认状态、业务确认人/来源。确认人未知写待指定，不虚构姓名。

每条 AC 用四要素表达，缺一项就等于没有可执行判据：

| 要素 | 要回答的问题 | 反例 |
|---|---|---|
| 场景 | 在哪个页面或业务域 | 写“系统”或留空 |
| 对象 | 哪个字段、功能或元素 | 写“数据”“内容” |
| 条件 | 前置、边界、角色、状态 | 写“一般情况” |
| 关注点 | 要验证什么可观察行为 | 写“正常”“成功”“符合预期”“无异常”“功能可用” |

四要素全部落到可观测的词上：对象能定位到页面元素或接口字段，条件能说出具体取值或角色，关注点能说出“改了什么、读回什么、保持不变的是什么”。结构化数据用 `elements` 承载这四项，`case_data.py --strict` 缺失或写空话即失败；教学表格可等价表达，但同样不能只写“功能正常”。

明确每条 AC 的必选 TC 组合：默认关联的全部必选 TC 均需满足；若多个观测路径为替代验证，须在执行前记录 OR 组合及等价理由，不能失败后临时选择通过路径。必选 AC 不得没有必选 TC。AC 执行状态从这些 TC 聚合：明确业务断言失败为 FAIL；否则存在 BLOCKED/NOT_RUN/SKIPPED 或未解决波动则待核实；全部有效满足才 PASS。REQ 的满足要求全部必选 AC 满足。非必选项仍保留发现与风险，不以必选标记免除严重产品缺陷。

例如“保存成功”需拆为已确认的结果：保存返回业务成功、刷新后能读回相同内容、列表显示新值；如存在异步更新，需明确完成信号与允许延迟。未给定性能数字只能提出建议并待确认，不能把自拟阈值当既定需求。浏览器可观察的读回是黑盒持久化证据，不能声称直接审计数据库事务。

关键断言还记录独立预期依据与判定方式（机械检查/专家判断/模型辅助/须真实执行）、规则来源版本或日期（可知时）、时间窗与误差、拒绝后应保持的不变量。不能复制被测算法或用同一响应同时计算预期与实际；HTTP200、toast、无控制台错误、截图正常、工具issues为空都不能独立替代业务结果。无法观测关键副作用时保留证据缺口，不以推测填PASS。

## 禁止断言清单

缺依据时保持待确认，不得用常识或模板补一个看起来合理的断言。以下按类型列出不能凭空断言的内容：

- **安全**：未声明加密方式不断言具体算法；未声明会话策略不断言超时时长；未声明脱敏规则不断言字段已脱敏；未确认角色清单不按数组顺序推断谁受限。
- **性能**：无量化指标（响应时间、并发量、吞吐量）时不断言达标或失败，也不自拟阈值当需求；单次采样不推出真实用户分布。
- **接口**：契约未给出时不断言具体错误码数值、字段必填性或分页排序规则；未知 endpoint 不得补造。
- **状态迁移**：需求未声明时不断言「非法迁移必须被拒绝」，只能记为风险假设并单独标注。
- **兼容**：不自行列出需求未承诺的浏览器或系统版本矩阵，只按产品支持范围采样并标注未测组合。
- **可靠性**：未声明重试、降级或幂等策略时不断言其行为，只验证实际可观测的结果与副作用次数。

上述内容可以作为探索假设或待确认项记录，但不得写成必选 AC 的通过标准，也不得据此判产品失败。结构化数据中空话会被 `case_data.py` 拒绝：AC 的 `description`/`oracle`、测试点的 `check`/`oracle` 若只剩「正常」「成功」「符合预期」「功能可用」这类词，直接判错而不只是提示。

界面样式、易用性和基础无障碍默认评估适用性并列实际可执行检查：样式结合真实状态/视口的几何、可读性与交互，UX核对可发现性、一致性、反馈、错误预防恢复、任务负担与数据保留，键盘焦点和语义标签以实际页面验证。设计差分需来源明确的基线；无基线仍能检查客观异常，主观偏好单列建议。具体观察和判定遵循 `visual-usability.md`，不声称专家启发式评审等同用户研究或完整无障碍认证。

## 判据登记要求

每条验收条件与缺陷判定须登记判据三要素，缺任一项不得作为正式判定依据：

| 要素 | 要回答的问题 | 反例 |
|---|---|---|
| 判据来源 | 依据哪条 REQ/AC/契约/明确不变量/已确认规则 | 写"经验""常识""一般来说" |
| 观测入口 | 通过哪个页面元素、接口或读回动作取得证据 | 写"看一眼""应该能看到" |
| 适用条件 | 该判据在哪些角色/状态/数据/环境下生效 | 写"所有情况""一般场景" |

- 有来源判据：可产出 FAIL/PASS 等正式结论，结论须随附三要素登记。
- 无来源判据：只能产出**待核验候选**（记录现象与候选判据、缺哪项来源），不得直接计缺陷或判 PASS；补齐来源后升级为正式判定。
- 模型自猜的规则、未经确认的历史对比、他例类比只能作为辅助线索进入待核验候选，不能独立构成判据来源。

## BDD 场景

Given 描述角色、业务前置和数据；When 描述一个业务事件；Then 描述可判定的业务结果及必要副作用。同一事件可有多个关联 Then 断言；不强制“一场景只能一个断言”，但避免混入多个无关业务目标。使用业务语言，将选择器、请求和数据库查询放到实现层。

以下为教学示例，所有阈值均为示例规则，实际执行前须由本次需求确认：

```gherkin
@REQ-NAME-01 @AC-NAME-01 @SCN-NAME-01
Feature: 修改项目名称
  Scenario Outline: 拒绝不满足名称长度规则的修改
    Given 编辑者打开一个自己可编辑的项目
    And 项目原名称为 "原名称"
    When 编辑者将名称改为 "<name>" 并保存
    Then 系统提示名称不符合长度规则
    And 重新打开项目后名称仍为 "原名称"

    Examples:
      | name                  |
      |                       |
      | abcdefghijklmnopqrstu |
```

若示例规则为长度 1–20，则至少设计长度 0/1/20/21 与空白、权限不足、保存失败、刷新读回等独立用例；未确认前均标为暂定。角色、项目和字符串需真实建数，不能仅靠 Given 文本假定已存在。

有 .feature 时检查步骤定义、参数化、测试数据和执行入口是否真实存在；无 .feature 时使用等价的结构化 G/W/T 场景并与执行步骤映射，不因格式缺失断言“没有 BDD”。文案存在、步骤可解析、脚本能编译均不等于本次已执行通过。

## 用例必填项

TC ID、REQ/AC/SCN 链接、标题、优先级、必选与否及理由、套件标签、链路模式、角色、环境前置、具体数据、步骤、每步必要预期、最终业务断言、观测入口、清理方式和可重复运行条件。参数引用需能解析到数据，不能只写“有效数据”“异常数据”。

数据驱动用例保留数据行标识；测试产生实体使用 RUN 标记或可核验归属标识。不能控制外部真实数据时保留缺口，不任意修改他人记录。

## 页面状态、探索与条件专项映射

实际观察的页面/组件、动作、角色、视口、状态及数据组合关联现有FP/SCN/PATH/TC/EXP/RUN，不重建平行编号或修改既有设计schema。默认/加载/空/错误/成功/禁用/无权限和弹窗/抽屉/页签/焦点等状态记录实际触发方式、前置与证据；无法触发列缺口，不能从静态截图推定状态已覆盖。未探索入口、选择依据及停止原因按 `exploration-runtime.md` 记录；候选不等于规格事实、授权或执行结果。

页面到接口的链路使用实际method/path、请求业务ID和脱敏参数/响应，比较页面提示、接口业务结果和最终读回；未知endpoint不得补造。接口契约检查覆盖本次范围的必填/类型/范围/错误码/分页排序/版本兼容，协议来源未知则暂定。跨角色/用户/租户矩阵记录实际获授权账号与自有数据，账号缺失保留缺口，不由一个账号外推隔离正确；可见请求不授予任意重放、篡改或跨对象访问权限。

涉及写入、任务、导入或订单时，TC按确认规则写清重复提交/幂等语义、业务关联ID、副作用次数、事务策略（全回滚或允许部分成功）、异步完成信号、超时查询与恢复。有限双击、重复/延迟/乱序回调、故障注入只有在相应环境和授权下执行；黑盒仅报告实际读回，不能据此证明内部原子性。超时结果未知先查原任务，不以新提交替代恢复。

按业务触发为本地存储/离线同步/导入导出/迁移、电商促销订单库存售后、埋点与外部平台、网站AI功能、容量可靠性补相应TC与缺口；具体清单见 `methodology.md`。离线冲突/迁移策略、优惠/库存/金额规则、事件次数/属性、AI质量量表、性能阈值均需来源，不能从示例或常识设定产品标准。采集工具与AI输出只是材料，需专家复核可执行步骤、独立断言及证据边界。

## 前置与测试数据的可复跑检查

设计完成后、执行前，以及换人/跨会话复跑前，核对以下条件并记录检查依据；已有真实记录可引用，不重复抄写。检查结果为“已就绪 / 未就绪 / 待核实”，与用例执行PASS/FAIL分开。

| 检查项 | 需能回答的问题 | 未满足时处理 |
|---|---|---|
| 目标与版本 | 网址、环境、应用/规格版本、开关与本轮一致吗 | 差异记录并按执行管理契约新建轮次或补充核对，不继承旧PASS |
| 角色与初始状态 | 实际测试角色具备规定权限吗；实体、会话、业务状态如何核验 | 相关TC阻塞或待执行，不把“用户已登录”文本当实证 |
| 具体输入与来源 | 正常/边界/异常数据可取到吗；有效性与预期依据是哪条需求/AC | 记录数据准备方法、脱敏样例/引用及规则来源，不用空泛的“有效数据” |
| 准备方式与归属 | 数据由谁/哪轮创建，唯一标识是什么，是否允许修改，是否与别例共享 | 无法确认归属则不擅改；独立建数或列依赖缺口 |
| 外部依赖与观测 | real/sandbox/mock模式明确吗；结果读回、异步完成信号能取得吗 | 限定验证边界，不用模拟成功替代真实业务闭环 |
| 重复执行与恢复 | 再跑会不会重复扣减/提交；失败后如何恢复初始状态并保留证据 | 核对已有副作用和重置路径；只清理本轮归属且获授权的数据 |

检查缺项只阻塞依赖它的用例，其余明确且安全的部分继续。数值阈值、时间窗、期望状态逐项引用REQ/AC、原型或确认记录，并标明来源版本/日期（可知时）和适用条件。假设关联到具体规则、TC和结论，不能仅在报告开头写一句“存在假设”。缺业务阈值时保持暂定，不凭通用经验判失败。

结构化设计继续采用 `case-data-contract.md` 的现有字段；详细准备方法、来源、断言复核、状态映射与就绪记录可放manifest或数据说明并引用TC ID，不强制改schema或复制第二套规格。`case_data.py`可验证字段与引用，但不能证明账号权限、数据归属或实际环境已就绪。内部JSON/JSONL/YAML继续按原生产者—消费者契约使用；对外交付的结果、问题及覆盖视图用UTF-8-sig逗号分隔CSV，不能将内部JSON规范改称CSV或以派生CSV覆盖事实源。简单任务复用既有清单，不因这些检查额外增加审批。

## UAT 与技术验证

技术验证状态来自真实执行。业务签收单独记录需求/版本、确认人、时间、接受/不接受/待确认、说明和来源。技术通过且无人签收时写“技术验证通过；业务待确认”。若业务方否认标准，则回到规格澄清，保留此前执行记录，不补造签收。
