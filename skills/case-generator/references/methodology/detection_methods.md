# 检出方法学：从"看到了"到"判得出"

> 执行期使用，尤其在一个页面"看起来正常"、但你不确定是否真没问题的时候。
> 与 `design_methods.md` 的分工：那份讲**怎么设计用例**，这份讲**怎么把观察变成可判定的缺陷结论**。
> 盲测的 `required_branches` 与本文件的"可判定信号"一一对应；`hidden_answers` 从 `defect_patterns.md` 取模式，不随手编。

---

## 1. 判定链：缺一环就不能记缺陷

```
现象（我看到了什么）
  → 差异（与什么不一致）
    → 判据 oracle（凭什么说它是错的）
      → 影响（谁会受影响、多严重）
        → 证据（别人能否复现）
          → 结论（FAIL / 待确认 / 建议）
```

常见错误是跳过第 2、3 环直接写缺陷：**"按钮点了没反应"** 不是判据；**"点击「保存」后 3 秒内既无请求也无提示，与需求 3.2「保存需即时反馈」不符"** 才是。

## 2. Oracle 六源（判据从哪来）

| 来源 | 适用 | 示例 | 不适用时 |
|---|---|---|---|
| 明文规则 | 需求/AC/字段约束/接口契约 | 名称 1–20 字符，21 应拒绝 | 规则缺失 → 记待确认，不自造阈值 |
| 同类一致性 | 同页/同产品同类控件 | 同列表其他列可排序，此列不能 | 只有一处实现 → 不能据此判错 |
| 守恒 | 数量/金额/状态/计数 | 勾选 3 条恢复后回收站应减 3 | 存在并发/异步 → 需读回确认 |
| 可逆性 | 增删改与撤销 | 彻底删除后不可恢复 | 有回收站策略 → 按策略判 |
| 幂等性 | 提交/支付/创建 | 重复提交不应产生两条记录 | 需求明确允许重复 → 不判错 |
| 外部标准 | 无障碍/文案/安全基线 | 焦点可见、错误提示指明字段 | 未承诺等级 → 只记建议 |

一条缺陷尽量挂**一个**最强 oracle；多个 oracle 互相矛盾时，先记"待确认"并写清冲突点。

## 3. 可判定信号（正常态看不出来，异常态才暴露）

按用户目标分七类；每类给"怎么触发"和"看到什么才算数"。

| 类别 | 触发方式 | 可判定信号 | 结论下限 |
|---|---|---|---|
| 功能 | 改输入/改顺序/改入口 | 操作成功但数据未变；成功提示后读回为空；同一操作两种结果 | FAIL（需读回证据） |
| 数据 | 边界值、特殊字符、超长、并发 | 截断无提示；精度丢失；排序/分页错位；跨页丢选择 | FAIL |
| 状态 | 中断、返回、刷新、双开 | 状态残留（已驳回仍显示待审批）；进度卡在中态；返回后筛选被重置 | FAIL |
| 权限 | 换角色、直连 URL、改请求 | 低权账号可执行高权操作；无权时页面空白无提示 | FAIL（安全类升级严重性） |
| 界面 | 改视口、长文、空态、暗色 | 元素重叠/截断；空态无引导；对比度不足；错位只在第二内核出现 | FAIL 或 待确认（视口≠内核） |
| 易用 | 键盘、连续操作、误触 | Tab 跳过主按钮；无焦点可见；危险操作无二次确认；错误提示不指明字段 | FAIL（无障碍按基线） |
| 文案 | 变量、术语、单位、时区、异常 | `{{name}}` 未渲染；同对象两种叫法；金额单位缺失；时间用 UTC 显示成本地 | FAIL（客观错误）/ 建议（偏好） |

**触发纪律**：不要等"已经明显坏了"才查。默认态正常时，按上表主动构造一次异常态（断网、5xx、重复点击、返回、换角色、第二内核），再决定有没有问题。

## 4. 证据最小集

| 结论 | 至少要有 |
|---|---|
| FAIL | 复现步骤 + 预期（含 oracle 出处）+ 实际 + 一条可复核证据（截图/请求响应/读回） |
| 待确认 | 冲突的两条依据（如需求 vs 实现、两处同类不一致） |
| BLOCKED | 缺什么（账号/环境/数据）+ 影响范围 + 谁可以解除 |
| PASS | 执行过的分支 + 实际观察（不能只写"正常"） |

证据文件名要能自解释（`21字符-保存成功-20261118.png`），不写 `1.png`。

## 5. 六态与结论上限

`PASS / FAIL / BLOCKED / NOT_RUN / SKIPPED / 待核实` 六态**不得互相冒充**：

- `warn`（如相似用例提示）不等于业务 PASS；
- 同视角另一条 PASS 不能清掉本条的 BLOCKED；
- 只观察未断言 → 最多"待核实"，不能写 PASS；
- 外部工具（figma/接口）的 fail 未回写清单时，只能列"外部结论缺口"。

## 6. 什么时候只能写"待核实"

- oracle 缺失且无法从一致性/守恒推导；
- 环境不具备（无第二内核、无第二角色、无邮件服务），且未取得豁免；
- 只做了观察，没有可重复的判定动作；
- 需求内部矛盾，产品未裁定。

这四种情况**不算漏测**，但必须写进报告并列入未测义务；把"待核实"写成 PASS 才是漏测。

## 7. 与盲测的对应

| 盲测要素 | 本文件对应 |
|---|---|
| `required_branches` | §3 每类信号的触发方式，逐条落成分支名 |
| `hidden_answers` | §3 的"可判定信号" + `defect_patterns.md` 的模式 |
| `legit_near_misses` | `false_positive_guard.md` 的合法近似反例分类 |
| 证据完整率 | §4 证据最小集 |
| 未测义务 | §6 的四种"待核实"情形 |

执行方在盲测里只需交付"现象 + 判据 + 证据"，不需要也不应该知道答案键。
