# 证据等级：E1 实测 / E2 模拟 / E3 未执行

> 用途：交付前给自己的每句结论定级，防止"模拟当实测""产出当验证""跳过当通过"。
> 与 `execution-evidence.md` 的关系：那份定义 PASS/FAIL/BLOCKED 等**执行状态**，本文件定义**证据强度**；两者交叉使用（E1+PASS 才是干净通过）。
> 来源：改编自本机专家 `test-automation` 的 其 `evidence-grading.md`，按砺衡的执行状态与报告口径重写。

---

## 1. 三级定义

| 等级 | 判定（须全部满足） | 允许表述 | 禁止表述 |
|---|---|---|---|
| **E1 真实执行** | 在真实环境实际操作/请求；保留原始输入与完整输出；UI 有截图或 DOM 快照；记录版本/环境/角色/数据 | "已执行：12 通过 / 3 失败 / 1 跳过"；"失败见证据 X" | 无输出的"应该没问题"；把跳过算通过 |
| **E2 模拟执行** | 用视口缩放代替真机、jsdom/桩服务代替真实接口、静态扫描代替运行、契约比对代替调用 | "在模拟环境下验证了逻辑分支，未覆盖真实渲染与网络" | "测试通过，可以上线"；省略模拟边界 |
| **E3 未执行** | 只产出用例、脚本、计划或清单，未在任何环境运行 | "已产出 N 条用例，**尚未验证**" | "已验证""预计可以通过" |

**E2 必须声明不覆盖**：真实浏览器渲染与布局、真实网络与时序、真实文件系统与权限、CSS/视觉表现、原生事件与手势。

## 2. 与砺衡执行状态的映射

| 证据等级 | 可对应的执行状态 | 结论上限 |
|---|---|---|
| E1 | PASS / FAIL | 按断言与影响判"通过/不通过" |
| E2 | 只能记"待核实"，不得记 PASS | 待核实（写明模拟边界） |
| E3 | NOT_RUN / SKIPPED | 待核实（列未测义务） |
| 任意 | BLOCKED | 待核实（写缺什么、影响范围） |

规则：**状态是 PASS 但证据等级是 E2/E3 的，一律降为"待核实"**；反之 E1 但无断言，也只能"待核实"（测了不等于测对）。

## 3. 计数口径（与报告一致）

- **通过**：E1 且断言全部成立，无跳过；
- **失败**：E1 且有断言失败，附错误原文；
- **跳过**：未执行（环境不支持/依赖缺失/主动跳过），逐条写原因；
- **阻塞**：环境/权限/数据导致无法执行，属证据等级下降，不计通过；
- **禁止**：跳过、阻塞、E2、E3 计入通过数；用"基本通过""大致没问题"替代分项数字。

## 4. 表述对照

| 实际状态 | 错误说法 | 正确说法 |
|---|---|---|
| E3 产出脚本未跑 | "测试写好了，应该没问题" | "脚本已产出但未执行，需在目标环境跑一次" |
| E2 视口缩小验证 | "兼容性测试通过" | "1440/1280 视口下布局正常，未验证第二内核" |
| E1 只跑了部分 | "测试通过" | "已覆盖 A/B，C 本次未执行" |
| 失败原因不明 | "可能是环境问题" | "原因未定位，原始报错为 X，需 Y 才能判定" |
| 有多条跳过 | "基本都通过" | "12 通过 / 0 失败 / 3 跳过，跳过项为 X/Y/Z" |

## 5. 交付前自检五问

1. 每个"通过"，用户能看到对应执行输出吗？
2. 拿这份报告去质问开发，证据站得住吗？
3. 有没有哪句肯定结论是在没运行的情况下写的？
4. 本次未覆盖的部分写清楚了吗？
5. 挑剔的测试经理会先质疑哪一句？

任意一问答不上来，回去改报告，不要交付。

## 6. 与盲测的关系

盲测里"证据等级"直接决定计分是否成立：

- 执行方 `findings[].evidence_grade` 若不是 `E1`，该条不计检出，记"证据不足"；
- 必选分支标 `EXECUTED` 但只有 E2 证据的，分支执行率不认；
- 报告中"未执行"与"模拟"必须分开列，不得合并成"已验证"。
