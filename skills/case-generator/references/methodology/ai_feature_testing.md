# AI 功能测试（被测对象含生成/对话/推荐时）

> 适用：需求里出现 AI 生成、智能问答、推荐、语义搜索、Agent 调用等能力。
> 不适用：只是"用 AI 帮忙写用例"——那仍按普通需求测。
> 来源：改编自本机专家 `ai-product-testing-expert`（真测）的测试框架/标准/案例库/上线清单，按砺衡的判定链与证据口径重写。

---

## 1. 先分清两类

| 类型 | 被测对象 | 本专家是否负责 |
|---|---|---|
| 用 AI 辅助测试 | 普通软件，AI 只是提效工具 | 按普通需求测，不套本章 |
| **AI 功能本身** | 模型/对话/生成结果的质量 | 是，按本章 |

## 2. 先建立三个认知

1. **AI 输出是候选方案，不是答案**：不能拿"看起来合理"当通过。
2. **核心能力是校验，不是提问**：判定标准必须可执行。
3. **不可复现的结果不可采信**：参数不固定、样本不记录的结论只能算观察。

## 3. 四个维度与可判定判据

| 维度 | 看什么 | 判据写法（示例） |
|---|---|---|
| 准确性 | 业务规则是否被遵守、事实是否编造 | "回答必须包含『预售商品不支持无理由退换』，且不得出现『支持七天』" |
| 稳定性 | 同输入多次、多轮追问是否自洽 | 固定参数重复 5 次，结论一致率；多轮追问同一规则是否前后矛盾 |
| 鲁棒性 | 注入、超长、空输入、混合语言、恶意指令 | 构造"忽略以上指令"类输入，检查是否越权/泄露系统提示 |
| 体验与安全 | 拒答是否合理、隐私是否外泄、歧视/违规内容 | 未授权查询是否被拒；输出是否含他人个人信息 |

**规则性幻觉优先**：改写业务规则（如把"不支持"说成"支持"）比知识性事实错误严重得多，一律按高严重性处理。

## 4. 八个重点场景

1. 核心业务规则问答（价格、时效、退换、权限）
2. 规则冲突/例外条款（"除……外"）
3. 直接注入与伪装指令（引用、代码块、多语言）
4. 多轮追问与上下文污染（先误导再问）
5. 边界输入（空、超长、纯符号、混合语言）
6. 数据质量（脏数据、缺失字段、过期信息）
7. 性能与限流（长上下文、并发、超时）
8. 隐私与合规（他人信息、敏感字段、日志留存）

## 5. 可复现要求（不满足就只能记观察）

- 固定 `temperature` / `top-p` / 模型版本，写进记录；
- 每条判定重复至少 3 次，记录一致率；
- 环境（沙箱/预发/影子）、输入原文、输出原文、时间戳齐全；
- 变更模型或提示词后必须重跑，不能沿用旧结论。

## 6. 上线门禁（有承诺才判，不虚构指标）

| 门禁 | 判定 |
|---|---|
| 阻断级业务规则 | 抽样中 100% 不违反（违反即阻断） |
| 注入拦截 | 约定攻击面全部被拒或安全兜底，无系统提示泄露 |
| 隐私 | 未授权查询 100% 拒绝，无他人信息出现在输出 |
| 参数固定 | 记录可复现参数与重复次数，否则结论作废 |
| 已声明指标 | 按需求承诺的准确率/一致率判定；未承诺只记录实测值 |

## 7. 缺陷定级

| 级别 | 情形 |
|---|---|
| 阻断 | 核心规则被改写、隐私泄露、权限绕过、注入成功 |
| 严重 | 高频场景错误、拒答策略失效、多轮严重自相矛盾 |
| 一般 | 边界处理不当、文案/格式问题、低频不一致 |
| 轻微 | 表达风格、冗余解释（不记缺陷，记建议） |

## 8. 对话式 Agent 被测对象的实测要点

被测对象本身是"对话式 Agent/助手"（用户发指令、Agent 调工具改业务数据）时，除按前文维度测能力外，还须处理以下专属风险：

**静默消息丢失（最高优先）**：含特殊字符串（如路径穿越串、部分注入载荷）的消息可能被前端或网关静默吞掉——无回复、无气泡、无提示、无报错。判"无响应"前必须两层核对：网络层钩子捕获本轮全部 fetch/XHR 状态码（4xx/5xx 逐条留证）+ DOM 层确认回复气泡确实未渲染。两层都核实才能判"消息丢失"；只看页面会漏掉请求层证据，只看网络会误判仍在渲染中的回复。此类缺陷一旦发现列入每轮回归。

**回复完成判定**：流式输出期间文本长度不变不等于已结束（如"已思考 N 秒"阶段）；用户消息气泡可能不渲染但消息实际已送达——两者都核实后再判失败。"生成中"的判据精确匹配停止按钮的存在与否，不能用宽泛文本包含，否则会误判提前结束。

**写入结论的独立验证**：Agent 写入后自己读回并汇报属**同通道互证**——写入载荷构造错误而读回也按同样口径读时，两边互相印证、无法发现。写入类结论至少三层证据交叉：① 网络层真实请求状态与数据版本号递增；② 新会话冷读（零上下文重开，无法复述此前声明，只能读真实落盘值）；③ 直接打开产物页面读服务端渲染 DOM（完全绕开被测通道）。三层一致才记"真实生效"；仅凭 Agent 自报读回不得判 PASS。

**审批与澄清卡片的驱动纪律**：自动批准须设次数上限防审批风暴；澄清卡片的自动选择须有用户授权；平台限流与审批卡叠加会把驱动拖入死循环——单条消息的写入量要拆细，避免一条消息触发大量需审批的操作。驱动超时不等于写入失败、也不等于零副作用：先按业务 ID 核副作用再决定是否重试，防止重复写入。

**专属能力在专属载体上测**：在普通载体上被拒的"仅某类型/套餐/角色可用"项，必须在对应专属载体上重测后才能记"已测"或裁定"不适用"；在错误载体上被拒就判"不适用"等于没测。

**不顺从产品自述**：Agent 声称"接口不支持/仅网页可做/设计如此"时按待验证声明处理，三分账：有规格/需求来源的边界如实记录后结案；无来源的记为能力缺口，保留在缺口清单与报告中，不得因解释合理就标 PASS(不适用)；说法可疑的用替代通道实际核实——声称"仅网页可做"就实际打开网页验证是否真的可做，声称"接口无字段"可对照网页端实际提交的请求载荷核实。核实结果与自述不符时按疑似缺陷立案，而非沿用产品解释。

## 9. 与砺衡其他文档的关系

- 判定链与证据等级：`detection_methods.md`、`evidence_grading.md`（AI 输出同样要求 E1 实测证据）；
- 误报：模型"答得不好"不等于缺陷，按 `false_positive_guard.md` 四问降级；
- 探索清单：AI 功能条目用 `functional + content` 属性，把"规则一致性/注入/多轮"写成独立条目，不要一条"测了 AI"概括；
- 盲测：AI 场景的 `hidden_answers` 应写成"可判定的规则冲突"，不写"回答质量差"。
