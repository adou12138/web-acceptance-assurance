# 7.42 设计稿侧文本对比度

## 为什么放在设计侧

页面侧的 7.41 能发现「这行灰字在页面上不达标」，但那时设计稿和代码都已经写完了。
对比度不需要页面就能算——设计模型里有文字颜色、字号、字重，以及它每一层祖先的填充。
**在设计评审阶段就报出来，改一次成本等于零；等到上线前再改，要同时改设计稿和代码。**

这也是设计稿驱动测试独有的位置：任何只做页面的测试工具手上没有设计数据，
只能在页面做出来之后才看得到这个问题。

## 输入

`extract_design_fields.py` 的产物（必须含 `tree` 层级；只有 `flat` 时无法回溯祖先底色，
本维度记 `notRun` 并写明原因，不按白底硬算）。

```bash
python scripts/design_contrast.py --design ./parity-test/design_fields.json \
  --out ./parity-test/design_contrast.json
```

## 判据

WCAG 2.1 1.4.3（AA）：

| 文本类型 | 门槛 |
|---|---|
| 正文（< 24px，或 < 18.66px 且字重 < 700） | 4.5 : 1 |
| 大字（>= 24px，或 >= 18.66px 且字重 >= 700） | 3 : 1 |

严重度：对比度 < 3:1 记 `P2`；3:1 ~ 门槛之间记 `P3`（贴边不达标，改动量可能很小）。

## 底色怎么算：候选集合

Figma 的填充可能是纯色、渐变、图片。逐层向上合成时把底色表示成**候选集合**：

| 情况 | 处理 | 结论 |
|---|---|---|
| 祖先填充是纯色 | 用 alpha 合成到当前集合 | 可精确计算 |
| 祖先填充是渐变 | 对每个色标分别合成，集合变大 | 全部色标不达标 → `confirmed`；部分不达标 → `pending` |
| 祖先填充是图片 | 集合变为「未知」 | 一律 `pending`（拿不到像素，不猜） |
| 顶层画板无填充 | 按白底算，但标 `pending` | 透明最终落什么底色由实现决定 |
| 祖先 `opacity < 0.95` | 记 `pending` | 整组半透明，合成结果依赖下层 |

取候选集合里**最差**的一档作为结论——文字只要有一部分落在不可读的底色上，就是可读性问题。

## 不判定项

写进产物的 `coverageNote`，避免被读成「这块已经测过」：

- 图标/图形对比度（WCAG 1.4.11，属非文本对比度）
- 文字压在照片上的实际像素亮度
- 设计稿与实现是否一致（那是像素层与样式层的事）

## 与 7.41 的关系

同一件事的两端，不是重复：

- 7.42 报出、7.41 也报出 → 设计稿这么写、页面也这么做了，**确实要修**
- 7.42 报出、7.41 没报 → 实现时改善了配色（好事），或页面文字与设计稿不是同一节点（元素对应问题）
- 7.42 没报、7.41 报出 → 实现时改坏了，或页面用了设计里没有的样式

报告里两个维度相邻展示，方便直接对上这条链路。
