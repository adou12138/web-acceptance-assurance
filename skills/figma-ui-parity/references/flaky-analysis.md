# 跨轮不稳定性（flaky）分析

## 为什么需要它

`baseline_regression.cjs` 每次运行都往 `baseline/runs/` 落一份快照，但回归比较只用
「本次 vs 基线」的一次性差值。于是下面两种报告长得**一模一样**：

```
A 轮 fail=3，B 轮 fail=3  → 同样的 3 项一直没修（稳定的真缺陷，该进台账）
A 轮 fail=3，B 轮 fail=3  → 完全不同的 3 项轮流出现（不稳定判定，该先修口径）
```

混在一起，团队会开始不信任整份报告——而**不稳定的结论比没有结论更糟**：
它会让人把真缺陷也当成噪声忽略掉。

## 判据

- 翻转只按 **pass / 非 pass** 二分统计：这是唯一会改变门禁结论的边界。
- `pending → fail` 这种「同属未通过」的漂移不计翻转，但计入 `statusDrift`——
  它同样说明判定不稳，只是不影响门禁。
- 一次翻转都没有的维度不进榜单，**即使它常年 fail**。那说明它很稳定。
- 某轮该维度是 `notRun`（换档位 / 换策略）时**跳过该区间**，不把「没跑」算成「变了」。

## 输入兼容

旧版快照没有每维度结论（`checks` 键）。这类 run 记为 `legacyRuns` 并在产物里点名，
**不能**当成「该轮所有维度都没结论」静默跳过——否则历史越久越容易得出「一直很稳定」
的错误结论。

## 命令

```bash
python scripts/flaky_report.py --baseline-dir ./parity-test/baseline \
  [--min-runs 2] [--top 20] [--fail-on-flaky 3]
```

产物：

- `flaky.json`：每 key 的维度序列、翻转次数、翻转率、`verdict`
- `flaky.csv`（utf-8-sig）：每个（key, 维度）一行，含完整状态序列，可直接排序筛选

`--fail-on-flaky N`：任一维度翻转次数 >= N 时以 `rc=2` 退出。**默认不开**——
flaky 是「口径需要修」的信号，不是「本轮没通过」，用它卡发布会把二者混为一谈。

## verdict 取值

| verdict | 含义 | 处置 |
|---|---|---|
| `flaky` | pass 与非 pass 来回翻转 | 先查判定口径（时序/等待/数据依赖），别急着报缺陷 |
| `stable-pass` | 多轮都 pass | 正常 |
| `stable-fail` / `stable-pending` | 多轮同一个结论 | 真问题，进缺陷台账 |
| `drift-only` | 没跨 pass 边界，但状态在变 | 判定不稳，观察即可 |

## 常见翻转原因

| 现象 | 典型原因 |
|---|---|
| 7.33 / 7.40 翻转 | 等待时长不够，界面还在渲染就采样了 |
| 7.41 翻转 | 对比度背景回溯在暗色/图片底之间跳动 |
| 7.43 翻转 | 页面加载时有无弹层不确定，焦点陷阱一条时有时无 |
| 7.12 / 待确认项翻转 | 上一轮 pendingChecks 被并入报告，下一轮重出报告时没带 |
