## M1 契约解析自检与示例块归属

> **契约解析自检**：规则解析（必填/类型/长度/枚举/禁用词）完成后会做一层机械自检，把「规则自己没把握」的可疑项写进产物 `self_check`（`flow.py` 汇总为 `plan["contractSelfCheck"]` 并在 stderr 点名）：必填列有未能识别的取值且无一字段判必填（SC1）、字段说明写明必填但必填列判非必填（SC2）、表头有长度/枚举列却一个约束都没抽出（SC3）。自检**只留痕、不覆盖原值**——猜一个「正确值」会把可疑项变成看起来确定的假边界用例；审查与排错口径见 `references/doc_review.md`。
>
> **示例块与表格归属**：请求/响应示例支持任意代码块语言标签（`json`/`csharp`/`java`/`php`），块内的 `Content-Type:` 行与不换行空格（HTML 导出常见）会被剥掉，取第一个 `{` 起始的正文解析；仍解析不了的块进 `parse_warnings` 点名，不静默丢弃。ShowDoc 导出把标题写成列表项（`- # 2.2.1 请求参数格式`）时同样识别为标题，否则表格只能按出现顺序猜归属——请求侧子对象表会被塞进响应字段，基线的契约断言必然假 FAIL。同名字段（主表 + 查询条件表重复列举）按名合并并取更严的一侧（任一处必填即必填）。**子对象表**（`condition` / `answer` / `answer_item`，标题常是 `<div id="…"></div>2.2.2.1.1 题目查询条件（condition）` 这种锚点 + 裸编号）识别后字段登记进 `sub_objects`，**不平铺成顶层参数**——顶层不存在的键发出去会被服务端忽略，随后被判成「校验缺失」假缺陷；子对象不测这一事实同时进 `parse_warnings` 点名。`parse_warnings` / `self_check` 随 `generated_cases.json` 落盘，报告侧可直接引用。
>
> **表格画法与表格归属**：表格有两种画法——ASCII 竖线 `| a | b |` 与制表符框线 `│ a │ b │`（配 `┌┬┐` / `├┼┤` / `└┴┘` 边框，手工对齐的文档大量用后者）。只认 ASCII 竖线时整行不被识别，参数表会**整张消失**，顺序兜底转而去拿文档里第一张无关表格当请求参数（环境配置表 → 字段名变成「本地环境类」）、拿覆盖率矩阵当响应字段：产物看着完整，用例一条都打不中接口。三种竖线（`│` `┃` `｜`）都认；边框行按表格边界处理——`┌┬┐` / `└┴┘` 结束本表、`├┼┤` 跳过但**不打断**当前块（否则表头之后的行全部丢失），纯横线 `─────` 是正文分隔线、必须打断，否则上下两张无关表会被拼成一张。标题没说请求/响应侧时，先看**表头有没有参数名列**（参数/字段/属性/name/key…）：没有就判为说明性表格（环境配置 / 覆盖率矩阵 / 产出物清单）跳过并点名，不再按「第一张表就是请求表」硬分。多接口合并文档里，标题点名了**别的 action** 的参数表（`### 动作 1000108 —— …`）同样跳过并提示用 `--action` 单独解析——并进本接口会让 `homepage_id` 变成创建接口的请求参数，服务端忽略未知参数后返回成功，被判「校验缺失」假缺陷。整份文档一张参数表都没认出来时退回历史口径（第 1 张当请求、其余当响应）并告警，不让「表头写法没覆盖」变成静默的空契约。

---

**响应侧成功/失败拆分**：响应表按标题分两侧——`RESP_HINTS`（响应参数/响应字段/成功响应/成功返回…）归成功侧，`FAIL_HINTS`（失败响应/失败返回/错误响应/错误码/fail/error…）归失败侧并打 `resp_side=fail`。同名字段**按 (name, resp_side) 去重**，同侧取更严、跨侧不合并：失败响应表的「必填=是」说的是失败时才返回该字段，升级到成功侧会让成功用例断言一个成功响应里根本不存在的键（errormsg / errorcode 最典型），接口完全正常却必然 fail，且产物外观完整、极难归因。拆分后 `response_fields` 只留成功侧，失败侧进 `failure_fields`（同时参与契约哈希，失败表改动才会触发 STALE_BASELINE）；**没有任何侧别标题的契约不拆**，产物与改造前逐字节一致。`_resp_contract_keys`、K01/Y01 读 `response_fields`，不换口径就自动只断言成功侧字段。

**契约字段的作用域**：契约声明的是「响应里有这个字段」，不是「data 里有这个字段」——`result` / `code` / `message` 这类业务信封字段写在**响应根层**，OpenAPI 契约把嵌套对象展开成**点路径**（`data.owner.uid`、`data.items[].name`）。判据只有一个：`assertion_helpers.resolve_contract_key(data, root, key)` ——扁平键先查 data、再查根层，点路径按路径从根层解析（数组段「任一元素命中」即算存在，空数组记 `unverifiable`）。只做 `k in data` 的扁平成员判断，这两类键**必然**判缺失，接口完全正常也成片 FAIL，失败文案却是「缺少契约字段」——最像真缺陷的一类假缺陷。契约断言（`check_contract`）与 K01 双向 diff（`case_runner._check_contract_diff`）**共用这一个判据**：两处各写一份必然漂移（同一份响应，一处判通过、一处出高严重级缺陷单）。K01 的「冗余字段」比对另需`documented_top_keys` 把点路径归一成 data 顶层键，否则契约声明 `data.owner.uid` 时响应里的 `owner` 会被误报成未文档化字段。从根层/点路径命中的键会在断言消息里点名，「通过」与「字段确实在 data 里」不是一回事。

**action 抽取与空 action 守卫**：action 按三路规则抽取——① 标题 `[1000107]`（`ACTION_RE`）→ ② 文件名（同款）→ ③ 正文（`ACTION_BODY_RE`：`"action": "1001002"`、`action=1000107`、`动作标识：1000107`、`action 1001002` 等写法，引号/空白与分隔符交错容许）。三路全落空时 `flow.py` **默认 stderr 点名 + 随 `parse_warnings` 落盘**（不阻断：无 action 契约的结构类测试依赖放行路径），`--require-action` 升级 exit 2。为什么值这个钱：没有 action 的用例整轮无法定位接口，而成片失败且产物外观完整的形态最难归因——宁可停在这里让人看一眼。注意字段表里的 `| action | int | 是 | 动作标识 |` 是**字段定义**不是取值，不构成第三路命中。

## M2 防呆门禁（反静默失败 / 反漏测 / 反矛盾）

对"输入给错/漏了"已有启动级硬拦截（缺参数 / 路径不存在 / 适配层缺函数 / 占位符未解析一律报错退出）。在此之上，针对"做少了却静默产出完整报告""输入自相矛盾"内置五道运行期门禁：

1. **配置矛盾拦截**（`personal_config.config_consistency_check()`，深度与冒烟共用，启动阶段）——region 矛盾、设了 `WJX_CROSS_ENV` 但跨环境配置为空 → **fatal，exit(2)**；域名 vs region 启发式（如 `region=intl` 却用国内域名）→ **warn**（`WJX_STRICT_CONSISTENCY=1` 升级为拦截）。
2. **环境选择拦截**（`smoke_runner.select_smoke_env()` / `personal_config._select_env()`）——`--env` / `WJX_ENV` / 配置 `default_env` 指定的环境**不存在时报错并 exit(2)**，不再回退到第一个环境：静默换环境等于整轮测了另一个环境（域名/账号/租户/数据全不同），产物上看不出来，而跨环境纪律依赖「选中即正确」。未指定环境时仍取第一个（与旧行为一致）。
3. **覆盖率门禁（反静默缺漏）**（`api_test_runner.coverage_gate()`，收尾阶段）——应测维度由 `applicability.py` 自动推导——**该自动推导只在「生成用例 → `case_runner`」链路成立**（`case_runner.py` 读用例文件里的 `coverage_plan`）；**七步深度流程里自写用例跑 `api_test_runner.py` 时需自行声明 `COVERAGE_PLAN`**，该路径未引入 `applicability`，未声明则门禁打印跳过并返回；**只有 `PASS`/`FAIL`/`PRECONDITION_UNMET` 才算"执行过"**（`PRECONDITION_UNMET` 确实发了请求拿到响应，只是结论既非通过也非失败；不计入会让"跑过但被前置挡住"的维度被误报成覆盖率缺口），`SKIPPED`/`N/A` 不计入已覆盖，杜绝"把没测当成测了"；缺口记 `COV-*`【缺陷(覆盖率缺口)】进台账并高亮，**逐条与维度两级产生**——已生成却未执行的用例在跳过前先记一条（`case_runner._skip_uncovered()`），收尾门禁再兜底整维度缺失，两级不可互相替代；`WJX_STRICT_COVERAGE=1` 升级为 exit(2)；**只锁参与维度**（默认全开后的 `coverage_plan`），不再有「选测」这一档——选测不进分母，等于声明了却不参与。族名与用例维度不一致时（AF1/AF2/AF3 vs 声明 AF）统一走 `case_coverage.dim_matches()`：数字后缀属同族，字母续缀属另一维度，`A` 不会被 `AB` 冒充覆盖。

选测维度本轮零用例时，产物 `uncovered_optional_detail` 逐条给出原因，不只是维度字母：

| 原因 | 含义 | 该怎么读 |
|---|---|---|
| `no_feature` | 契约无该维度特征（未满足生成器触发条件） | 本接口确实无需测 |
| `response_side_only` | 有特征，但字段仅在响应侧，无法构造请求 | 需换思路，不能算覆盖完成 |
| `name_hit_only` | 接口名命中业务域关键词，但请求侧没有可传字段 | 功能可能存在于关联接口，建议查同源家族接口，别直接判本接口无需测 |
| `not_implemented` | 该维度无生成器实现 | **能力缺口，不是本接口无需测** |

只列字母时这三类长得一样，能力缺口会被读成「本接口无需测」并永久留在报告里，所以点名必须带原因。

**L 跨客户端兼容**走 `dim_generators.gen_client_variant_cases()`：靠改 `User-Agent`
模拟移动端 / PC 端 / 小程序三种客户端特征，与基线请求配对对比响应字段集合。服务端按 UA
分支返回不同字段集时，只有对应那端会解析失败，单端回归永远抓不到。这是**黑盒降级版**——
不同版本 SDK 的序列化差异与字段弃用兼容仍需多端环境，用例 note 里已写明，勿当作完整覆盖。

4. **约束对账门禁（反约束级静默缺失）**（`scripts/check_key.py`，生成期算出、执行期出声）——维度门禁只能回答「边界维度有没有用例跑过」，回答不了「契约声明了 `activity` 的类型，有没有一条 `wrong_type:activity` 用例」。生成器漏掉某字段的某个约束时，该维度仍被其他用例覆盖，维度门禁**看不出来**——这是静默缺口。每条用例带身份证 `check_key`：机械用例 → 约束型（`missing_required:name` / `wrong_type:age` / `above_maximum:title` / `below_minimum:code`），语义与人工用例 → 来源型（`semantic:xxx` / `manual:xxx`，同样纳入编号体系以保证可追溯）；门禁拿契约算出的**约束全集**逐条对账，漏一条即点名并给出契约原值。

   两条硬边界：① **来源型不进对账分母**——语义/人工用例不兑现字段约束，塞进分母会让门禁永远不可能通过，进而被人关掉；② **只出声、不进缺陷台账**——缺的是测试设计完整性而非接口缺陷，且单接口可达上百条（实测某接口 108 条），进台账会淹没真缺陷，完整清单留在产物 `check_key.missing` 供审计。

   `WJX_STRICT_CHECKKEY=1` 可将缺口升级为 exit(2)，与另外三道底层门禁的 `WJX_STRICT_*` 同套严格度约定。另有一条易被忽略的中间态：TODO 人工占位（`enabled=false` / `needs=manual`）按设计计入"已交付"（否则嵌套点路径字段每轮都会刷出永远兑现不了的假缺口），但当某约束**只有**占位兑现、0 条可执行用例时，产物会追加 `check_key.manual_only_keys` 并在报告中点名批次数量——真正的验证仍靠人工补齐。

5. **浅用例 / 空转检测**（反"报告看似完整但覆盖浅"）——仅断言 `result=true` 且无契约/增强断言的 PASS → 记低危观察并在汇总告警（`shallow_passes`）；`assert_non_empty()` 包裹自定义断言循环，集合为空导致循环 0 次恒 PASS 会被判无效（陷阱 17，`check_enum_exhaustive()` 已内建）；冒烟侧当前**没有**案例级「空案例」告警，也不响应 `WJX_STRICT_COVERAGE=`（`smoke_runner.py` 无此环境变量分支，其 `empty` 统计是响应**空值字段**而非案例级）；升级拦截仅覆盖深度流程；

> 设计原则：对"skill 自身输入错误"用硬拦截；对"做少了 / 静默漏测 / 输入自相矛盾"用门禁把风险从"靠人记"变成"靠代码卡"。上述底层门禁默认告警并留痕，显式设 `WJX_STRICT_*` 时升级为 exit(2)。统一入口 `flow.py --execute` 的运行完成判定更严格：结果必须完整、全 PASS、无**缺陷型** finding 和覆盖缺口（「待确认 / 环境风险 / 符合预期」类观察记录不阻断 done 判定，但会让 suite 无法晋升基线）；复测还须全部为 FIXED，否则标 failed 并返回 2，不受上述默认告警策略豁免。

## M3 产物回读校验（脚本跑通 ≠ 产物可交付）

前面三道门禁管的是"测得够不够"，这一道管**"写出去的台账还是不是那张表"**。

陷阱 7 要求台账用 utf-8-sig、逗号分隔、含逗号/换行/引号的字段用引号包裹——但那曾经只是**文档里的一句约定**，写盘代码没有任何机制保证自己做到。少一个 BOM、某列忘了引号包裹、列定义改了而渲染层没跟上，Excel 里就是整张表错位，而**脚本 exit 0、报告"看起来完整"**，要等开发打开文件才暴露。

`scripts/artifact_readback.py` 把约定变成可执行检查：读回自己刚写的产物，验编码 BOM、表头与列定义一致（顺序也算）、每行列数、编号非空且唯一、台账行数 vs `report_full.json` 里 `findings` 数、证据链六列（请求ID / TraceID / 证据路径 / 置信度 / 归因 / 复测状态）是否真落进了 CSV（`HTTP状态码` 不在回读校验范围内）。

```bash
python scripts/artifact_readback.py --dir .            # 有error → exit 1
python scripts/artifact_readback.py --dir . --strict   # warning 也算失败（或 WJX_STRICT_READBACK=1）
python scripts/artifact_readback.py --dir . --json readback.json   # 供门禁消费
```

`flow.py --execute` **执行完自动跑一遍**（结果落 `artifact_readback.json`），不用手敲。默认将 error 纳入运行完成判定：存在 error 时标记 failed 并返回 2；warning 默认告警，`WJX_STRICT_READBACK=1` 将 warning 也升级为失败退出。**必须排在 `report_enhance` 之后**：增强会重写 CSV，放在它前面校验的是即将被替换的文件。

**采集类字段由运行时自动填充**：`run()` 与 `assert_validation()` 都用局部包装把本次请求的 `http_code` 与响应头里的请求ID/TraceID（`X-Request-Id` / `X-Trace-Id` 等常见头名）交给台账，`call()` 返回值与 `_record_response_headers` 旁路缓存是数据来源。用局部包装而非在各分支逐一传参，是因为 `code` 只在函数入口拿得到，散着传必然漏，而漏掉的表现恰好是"那几列恒为空"——不报错的静默缺失。取不到就留空（空值是可见的"没采到"，填占位值反而是假的）。

**为什么单独一个脚本而不是塞进 `coverage_gate()`**：门禁跑在写 CSV **之前**（缺口要进台账），回读必须跑在写盘**之后**，两者时序相反、职责也不同（一个判"该测没测"，一个判"写出去的对不对"）。塞在一起会让写盘动作发生两次。

**报出问题该怎么读**：

| 码 | 级别 | 含义 | 典型成因 |
|---|---|---|---|
| `NO_BOM` / `DECODE` | error | 编码不对，Excel 会乱码 | 用 `encoding="utf-8"` 而非 `utf-8-sig` |
| `HEADER_MISMATCH` | error | 表头与 `assets/finding_columns.json` 不一致（含**顺序**不同） | 改了列定义但映射表没同步；或两套写盘路径表头不同源 |
| `ROW_WIDTH` | error | 某行列数与表头不符 | 列错位，或含逗号/换行的字段没被引号包裹 |
| `BLANK_ID` / `DUP_ID` | error | 编号为空或重复 | 空编号无法复盘引用；重复编号会让复测指向错条目 |
| `ROW_COUNT` | error | 行数与 findings 数不符 | 有 finding 静默丢失——台账与报告对不上 |
| `EV_COL_MISSING` | error | 证据链列缺失 | 台账无法支撑开发复现 |
| `EV_ALL_EMPTY` | error | **全部**记录的采集类证据列（请求ID/TraceID/证据路径）为空 | 采集链没接上，开发无法复现 |
| `EV_PART_EMPTY` / `EV_LEDGER_EMPTY` | warning | 部分记录无采集类证据 / 记录类列（置信度/归因/复测状态）未填 | 个别条目没采到，或归因环节跳步 |
| `NO_ARTIFACTS` | error | 目录里既没有台账也没有报告——**没有可回读的产物不等于通过** | 产物目录/路径给错，或本轮压根没落盘 |
| `NO_LEDGER` | error | 找到了报告却没找到配套台账，台账一次都没被读过 | 自定义前缀台账；请用 `--issues` 显式指定 |
| `NO_PAIRED_REPORT` | warning | 没找到同前缀的报告，行数这次核不了 | 台账与报告前缀不一致 |
| `MISSING` / `UNREADABLE` / `EMPTY` / `CSV_PARSE` / `JSON_PARSE` / `NO_ROWS` / `NO_FINDINGS_KEY` | error | 产物缺失、不可读、为空或解析失败 | 写盘被截断/格式损坏 |
| `BLANK_ROW` | warning | 台账里出现整行空 | 写盘时多余换行 |

**台账与报告按前缀配对，不按时间**：`X_issues.csv` ↔ `X_report_full.json`。一次运行常留下多个前缀的产物（`api_test_` / `chain_` / …），按最新时间挑会跨运行配错对，比出**根本不存在的"finding 静默丢失"**。找不到同前缀就降级为warning 并明说行数这次查不出来，不猜。

**覆盖缺口之外的单列**：零缺陷是合法结果（不是缺口），空台账不会被误报成问题；报告文件缺失只降级为 warning 而非 error——它只用于交叉核对行数，不该拦住"只有台账"的单份交付。

## M4 契约驱动的自动生成（推荐入口 · 解决"做少了"）

本 skill 的知识（31 维度框架 / 21 条缺陷模式清单 / 适用性矩阵 / 断言 helper）原本只是**文档**，每次靠人"读文档 → 设计用例 → 手写 Python"，覆盖率取决于当次注意力——这是"做少了却静默产出完整报告"的结构性根源。现把这些知识变成**可执行规则**：

```
契约 → 字段语义推断 → 适用性自动判定 → 缺陷模式匹配（清单 21 条；其中 19 条在 `pattern_engine.PATTERNS` 有可执行规则，另 2 条「内容安全」与「组合非法」分别由安全载荷清单和组合生成器覆盖；PATTERNS 另含 UI1 / AA 两条清单外专项） → 字段级变异 + 安全载荷清单 → 声明式用例 → 执行 + 覆盖率门禁
```

**安全载荷清单**（G 维度）：`assets/security_payloads.json` 按字段语义标签/类型挑选载荷类别（SQL 注入 / XSS / 路径穿越 / 命令注入 / CRLF / **内容安全：广告导流 / 违法违规 / 辱骂 / 色情低俗**），每类每字段限量生成，断言方向为「应被拦截」——被原样接受即缺陷，被正确拦截记「符合预期」（陷阱3）。内容安全类目的 `payloads[0]` 为字面样本、`payloads[1]` 为同句**变体绕过**样本（符号穿插 / 空格分隔 / 全角 / 拼音混写）——字面拦得住、变体漏拦即真实缺口；类目可自行扩展，`applies_to` 写对即自动生效（生成器按 `applies_to` 匹配，无需改代码）；涉政敏感类不内置样本，需从团队/监管词库接入。

**字段限额按族保代表**（`field_semantics.pick_by_family`）：空值四态（P07 前 6 个可选字段）、
响应 URL（前 5 个）、UI 代理（前 2 个）等字段数限额，不再按位置取前 N，而是先让**每个字段族**
至少一个代表入选、配额有余再按原序补齐（族 = `llm_role` > 语义标签 > 去常见后缀的词干）。
族内字段共享后端校验分支，按位置取前 N 会把排在后面的整个族砍掉——限额要砍的是
「同类项重复测几次」，不是「某一类分支整个测不到」。

**门禁如何被激活**：`applicability.py` 自动推导参与维度 → 写入用例文件 → `case_runner` 自动装载 → 收尾 `coverage_gate()` 比对「声明参与维度」vs「实际触及维度」。

**维度默认全开（`applicability.judge()`）**：不再按操作类型预设「必测/选测/不适用」矩阵——矩阵没列的维度直接判 N/A，会把「暂不支持」永久化，理由还写成「该操作类型不涉及」这种无法核对的话。现在先假设 32 个维度全部参与，再由 `_dim_conditions()` 逐条检查契约事实：有没有请求参数、几个参数、有没有状态/分页/附件字段、是不是写操作、业务域能否构造请求（复用 `dim_generators._domain_dim_resolve` 单一事实源）。条件不满足才标不适用，理由点名具体缺什么，零产出代号经 `REASON_TEXT` 翻成中文后才进 `na_proofs`。**只有显式 `--exclude-dims A,B` 才关闭特定维度**，且排除要同时做三件：出覆盖率分母、出用例集合、在 N/A 证明里留痕；只改分母会留下「不参与却仍生成用例」的假象，只删用例会让门禁报假缺口。维度归一用 `_normalize_dim()`（去尾部数字），排除单字母 `A` 不会误吃 `AA/AE/AB/AC/AD/AF`。`dim_excluded` 只在真有排除时才写，默认产物不新增键，避免 `cases_hash` 全量漂移。

**生成后的运行时校准（`case_generator.generate()`）**：`_dim_conditions()` 只能按契约事实**预设**参与，能不能真跑要等用例生成完才知道。凡是留在计划内、却连一条可执行用例都没有（只有 `TODO-*` / `enabled=False` 占位）的维度，一律转不参与：移出 `coverage_plan`、按 `ALL_DIMS` 顺序加进 `na_proofs` 并写明**缺什么**（缺签名/身份字段、无 trace 语义、缺页面基线、缺回调地址），同时在 stderr 出声。**占位用例保留**——它标了 `enabled=False/needs=manual`，执行时只记 SKIPPED、不记 `COV-*` 缺陷，是「要补什么」的唯一清单；删掉它只剩一句理由，人工补充点就被抹掉了。判据是**运行时事实**不是能力黑名单：换上带对应字段的契约，该维度自然回到计划内。只做到「部分可执行」的维度（如 E、AC 既有真用例也有占位）不降级——同一维度下别的用例跑过会让门禁判「已覆盖」，占位不记缺口就彻底静默了。

**三条默认开启的深度链路**（单接口就能跑满，不依赖其他接口的业务知识）：

- **越权矩阵（A）**：按「身份 × 操作面」铺开，而不是只给一条签名错误。身份轴跨企业 appid / 子账号 / 主账号对照 / 跨企业+主账号双重矛盾，操作面分写与读。读面用例是**配对对照**——先用本企业身份自证可读，再看跨企业身份能否读到；本企业也读不到时不判越权（那种拒绝多半是缺参数，判成"隔离生效"是假的通过）。身份一律用 `<跨企业appid>` / `<子账号>` / `<主账号>` 占位符承载，配置缺哪一项就点名跳过，绝不填空串冒充。
- **交叉验证（C1）**：主接口说成功不算数。`companion_scan.py` 解析配套接口（命令行 > 契约显式声明 > 同级目录扫描 > L5 知识库候选，扫描只在业务对象名对得上时才采用并写清置信度；知识库候选带模糊成分，只进候选清单不自动填，供人工 `--read-action` 指定），拿到读接口就做真往返，拿到列表接口就验「创建后资源出现在列表 / 总数 +1」。拿不到就留空并在待补清单点名，不拿主接口响应假装验过。计数基线在主请求**发出前**采集——check 内两次取数都已落在操作后，差值恒为 0。
- **状态机与幂等（E / AC）**：有状态字段就跑**转换矩阵实测**（逐个目标状态提交 + 回读，产出接受/拒绝事实表）；合法性是业务语义不猜，只硬判「接受了但回读值被改写」这一确定缺陷。幂等与并发重复提交不依赖唯一键也能测：创建类接口重复提交产生多个对象只记观察（业务本就允许多条），结果漂移才判缺陷。
- **零产出维度补齐（`dim_generators.py`）**：编码国际化 I（多字节 / emoji 代理对 / 全角 / RTL）、组合交叉 F（多字段同时异常）、请求追踪 V（标识非空且逐次不同）、批量 X（100 条与混入非法项）、导出下载 M（须给出可用下载凭据），以及按**字段特征触发**的业务域专项 N 层级 / Q 角色 / W 附件 / S 分类 / T 账号 / O 通知 / P 分享 / R 报告 / U 导入。三条约束：契约没有对应字段就不生成（造出来的是噪音，还会让"该维度已覆盖"变成假象）；预期说不清的（如顶级节点 parent 为空是否合法）一律 P2 + note 说明"业务允许则记符合预期"，不制造假缺陷；识别不到追踪/下载字段时记观察而非缺陷。

**已知边界**：确实拿不到输入或观测通道的检查（事件推送需推送日志、时区口径需页面时间显示值、批量部分失败需批量接口）标 `needs=manual`，执行时跳过、但**跳过前先记 `COV-*` 缺口进台账**——结果行上的 `SKIPPED` 不进台账，只有台账会被交付与复盘看到，不静默丢弃；生成用例是起点不是终点。模块清单见 `references/auto_generation.md`，降级阶梯与写操作门禁见 `references/intelligence_policy.md`。

### 发现档（discovery：集中放宽探测广度）

规则引擎默认把"探测广度"的限额拧在保守值上，而这些限额散落在生成链的不同阶段
（超长用例上限、安全载荷每字段每类条数、字段族配额、AF 业务场景条数）——想"多探一点"
要分别改多处，且容易只改一半。`scripts/discovery_profile.py` 把它们收成一个档位，
`--profile discovery`（或 `WJX_PROFILE=discovery`）一处生效：

| 限额 | 默认档 | 发现档 | 影响 |
|---|---|---|---|
| 超长用例上限 | 5000 | 20000 | 让 max_len 数万级的字段也能构造真正的边界用例 |
| 安全载荷/字段/类 | 2 | 4 | 每字段每类多测字面 + 变体绕过样本 |
| 空值四态字段数 | 6 | 12 | 更多字段进入空值 / 缺失探测 |
| 响应 URL 字段数 | 5 | 10 | 更多 URL 字段做"真能打开"校验 |
| UI 代理字段数 | 2 | 4 | 更多字段做 UI 代理参数探测 |
| AF 业务场景条数 | 8 | 20 | 业务语义用例也随"多探"放大 |
| 大字段单探 | 关 | 开 | 对超限大字段追加一条"大内容健壮性"探针 |

三条硬边界：① **只放宽探测广度，不改断言口径**——放宽后用例的预期方向不变，
否则假阳性暴涨；② **默认档的限额与接入前完全一致**——不传档位时探测广度零变化
（增量接入；生成逻辑自身的修复不在此承诺范围内）；③ **放宽产生的用例不享受任何豁免**——
照常进分层统计、照常计入覆盖率门禁、照常可能被判缺陷。"多探"是增加探测面，
不是放松判定标准。

**复合类型的类型错误（`wrong_type`）**：契约写 `null / boolean`、`integer / string(int32)`
时，`type_bad_for` 按类型 token 逐个尝试，选一个**对每个成员都非法**的值注入——
若注入的值恰好命中某个联合分支被判合法，就会得到"类型错误被接受"的假缺陷，
因此所有候选都至少被一个成员接受时宁可跳过（返回 None），不冒险造假缺陷。
生成器补上这部分用例后，约束对账门禁里对应的 `wrong_type` 缺口随之闭合。

## M5 用例分层与造值语义化（避免"看起来覆盖很好"）

自动生成会产出两类用例，混在一起看会**高估覆盖**：

| tier | 含义 | 典型来源 |
|---|---|---|
| `business` | 业务与语义驱动 | 往返验证、交叉验证、状态机、越权矩阵、AF 业务场景 |
| `probe` | 机械探测：字段 × 固定算子展开、载荷清单遍历 | `B-MISS-*` / `B-NULL-*` / `B-OVER-*` / `B-TYPE-*` / `B-LEN-*` / `G-*` |
| `manual` | 待人工补充的占位 | `TODO-*` / `needs=manual` |

机械探测有覆盖价值（确实探到了某类校验是否存在），但**不代表业务场景被测过**。产物里给 `tier_stats`，`--print` 与落盘摘要都打印分层构成，**probe 多于 business 时告警**——此时「用例数」与「维度覆盖率」都是被撑高的，真实业务覆盖以 business 条数为准。分层**不影响执行与门禁**：probe 用例照常执行、照常判 PASS/FAIL、照常计入覆盖率。

造值同样做了语义化，避免一批用例打在同一个分支上：

- **类型错误**不再所有 string 字段统一填 `12345`，而是按字段序轮流取数字 / 数组 / 对象。后端对这三类非法值的处理分支不同（隐式转字符串 vs 直接报类型错），统一填一个值会产生一批重复的 PASS。数值语义字段固定用数字——数字转数值字段的隐式转换最容易出问题。
- **长度边界**用业务形态内容填充（如 `Overlong title ` 重复）而非 `'x'*n`，顺带覆盖转义与截断。刻意用 ASCII：中文的「按字符 vs 按字节」口径不一致（100 汉字 = 300 字节），会让「恰好 max_len 应成功」在按字节校验的后端上必然失败，那是口径差异不是缺陷，混进来会污染边界结论。
- **安全载荷**只对「内容会被存储 / 回显 / 拼接 / 渲染」的字段注入。标识类字段（创建者、枚举、各类 id）注入无风险含义，只会得到重复 PASS。判定不了时按内容型处理（宁可多测，不可漏测安全），被跳过的字段记入产物 `payload_skipped` 留痕，**不静默消失**。

## M6 重复与矛盾（用例条数能不能当覆盖证据）

用例池里有两类「看起来有用、实际没有」的条目：

| 现象 | 为什么有害 | 产物字段 |
|---|---|---|
| 同维度 + 同参数 + 同期望（同一个请求跑两遍） | 条数虚高，两条结果必然一致，不增加任何信息 | `duplicate_report` |
| 同参数，一条期望成功、一条期望失败 | 两者不可能同时成立，跑起来至少一条产出假缺陷 | `expectation_conflicts` |

判据是**签名判等**，不是相似度：`scripts/case_signature.py` 取 `(维度, 参数, 期望)` 规范化 JSON 的 SHA256。相似度两个方向都会错——实测真实 133 条用例池，jaccard 0.80 在同族不同字段的用例上判重率 93~95%（把不同字段判成重复），而 20 组真重复一组都没判出（0.68~0.75 未达线）。根因是中文没有空格，按空白分词会把整句当成一个 token，相似度实际度量的是「共享脚手架有多少」。

- **默认只统计不折叠**：折叠会改变用例总数，历史基线的覆盖率口径跟着变。加 `--dedup` 才真折叠，被合并用例的名字/类别/证据并入首条的 `merged_intents` 与 `evidence`，不丢意图。
- **矛盾只报不挡**：`success` 方向相反的组点名为 `CONFLICT`；`success` 一致但断言不同的只计数——各维度断言不同字段是正常复用，不该报成矛盾。
- 判重与矛盾都跳过 `enabled=false` / `TODO-*` / `needs` 非空的占位项：它们不是真实请求，参与判定只会制造噪音。

## M7 排除参数（`--exclude-params`）

有些参数不该围绕它生成用例：鉴权令牌、环境标识、固定的信封参数。`--exclude-params`（可重复传）把它们移出生成范围，同时保证请求仍然合法：

```bash
python scripts/flow.py --contract <路径> --exclude-params "token=abc123" --exclude-params env
```

排除参数也可以走**配置文件通道**，把某个项目固定要排除的参数清单固化下来：

```bash
python scripts/flow.py --contract <路径>                          # 自动探测配置（四级回退）
python scripts/flow.py --contract <路径> --exclude-config my.json  # 显式指定
```

**四级回退（替换语义）**：`--exclude-config` 显式指定 > `assets/exclude_params_<project>.json`（项目级，project 取 `--project`/`WJX_PROJECT_NAME`，如 wjx 与国际版两个独立项目各建一份）> `assets/exclude_params.json`（通用/单项目约定）> `assets/exclude_params.default.json`（**出厂兜底**，随仓库分发）。**第一个存在的文件就是基底清单，层与层之间不合并**；`--exclude-params`（CLI，可重复传）在基底上**只追加**——名字集合只增不减，同名条目**带值的覆盖前者**（包括覆盖先前的裸名），裸名只登记名字、不清掉已配置的值（裸名 = 「不赋值」，不是「赋空值」）。配置文件形态 `{"exclude_params": ["name", "name=value", ...]}`，条目语法与 CLI 一致；以 `_` 开头的键忽略，可留作说明。项目级/本地文件**按个人配置同样处理：gitignore 覆盖不上传，仓库只提交空白示例 `assets/exclude_params.example.json`**——真实清单可能含项目内部约定，与 `personal_config.json（真实配置不随包分发，用 personal_config.example.json）` 同一纪律。

- **不产任何用例**：有效排除集在契约副本上过滤——**总是执行**（出厂兜底保证 fresh clone 也非空），9 个生成器、约束对账分母（`check_key`）、模式引擎自动不再围绕信封键工作；信封键的 `missing_required` 不再进分母（永久假缺口由此消除）；
- **执行期注入联动**：`envelope_keys = 有效排除集 ∩（契约参数表字段名 ∪ 请求示例键）`，随产物落盘并驱动执行期——**契约里声明了的信封键由引擎注入（wjx 报文形态不变），契约没声明的（如内部接口）自动不注入**，零开关按接口区分；判定结果随 stderr 出声，`--envelope-keys "a,b"`（显式指定，必须 ⊆ 有效排除集）与 `--no-inject`（全不注入）可覆写，两者互斥。判定为 0 且契约未解析出请求示例时**单独点名**——「接口本来不用信封」与「示例块没解析出来所以判不到」在产物上一样，后者会让整轮请求因缺公共参数被拒；
- **请求仍携带**：值优先级 `CLI 显式值（name=value，按契约声明类型强转）> 引擎注入（信封键）> 请求示例值 > 契约默认值`；无值可用且非信封键时报错拒绝生成——值缺失会让全量用例假失败，比不生成更糟。**信封键永不取自契约示例**：示例里的 appid/sign/ts 是文档举例值（多半属于另一个环境或已过期），种进基线后经 `extra` 覆盖执行期注入的正确值，整轮请求会被当前环境拒绝；
- **基线退化留痕**：契约没写示例且字段没写默认值时，按类型造值（int→0 / string→"test"）只是让请求结构完整，**不是真实基线**——每个造值字段都进 `needs_manual_baseline`（产物顶栏 + stderr 点名）。按 id 查询类接口里 `vid=0` 是必不存在的资源号，拿到满屏失败时先看这一栏；
- **值按字面量发送**：`name=value` 里的值不做二次解释——`token=abc123` 原样发 `abc123`；只有 skill 已认识的占位符（`<APPID>`/`<主账号>` 等，见 personal_config）会在执行期解析，任意 `<token>` 写法**不会**被解析、会原样发出。参数名与值的**两侧空白会被去掉**（内部空白原样保留）——值本身首尾需要空白的场景无法用本机制表达；等号后为空（`name=`）不是合法条目，解析期直接拒绝并给出两条出路（只写参数名走值回退；确要空串在契约示例里表达）；
- **未声明条目直接忽略**：排除集里写了 `name=value`，但该名字既不在契约参数表也不在请求示例里（拼错、或那份契约确实没有这个参数）→ **不种进基线、不进请求**，`value_source` 记 `ignored_undeclared`、单独落 `ignored_exclude_params` 并在 stderr 点名。旧实现照常种进 base，于是每条请求都带一个服务端不认识的键，而服务端忽略未知键时用例照样「成功」——配错了也看不出。裸名不走这层判定（裸名不带值，不存在「塞进请求」的问题）；与某个声明名只差大小写时会在错误/告警文案里点名；
- **留痕**：明细随产物 `excluded_params`（name / value_source / value）落盘，`contract_model` 与回归基线哈希同步不含被排除字段（移出测试范围是有意变更）；
- **报告可见**：执行期装载进 `report_full.json` 的 `excluded_params` 与 `envelope_keys`，`case_runner` 启动时打印排除清单与注入键集——否则「用例比契约字段少」在报告里看着像漏测，而不是像按要求排除；
- **与 `--cases` 的关系**：`--cases` 执行已存用例时不重新生成，排除与注入判定已在生成期固化，同时给出时上述生成侧参数被忽略并提醒；旧 cases 文件未携带 `envelope_keys` 键时，执行期回退到与改造前**逐键一致**的 5 个固定键（`encode/appid/action/ts/sign`，内部 `_LEGACY_ENVELOPE`）——不是「任意键全注入」，所以旧产物上配了再多的 `--exclude-params` 也不会把未知键注进请求；
- **AF 业务场景链路不适用**：`business_scenarios.py --prep/--merge` 直接读原始契约、不经本机制，被排除参数在 AF 用例里不会被自动剔除或补值——用 AF 链路时需人工在 AF 提示词阶段剔除该字段并补上固定值；
- **A 维度探测门控**：A01（错签名）/A02/A06（跨企业 appid）的注入以「契约声明该键」为前提——内部接口契约没声明时降级为 `TODO-A-sign`/`TODO-A-appid` 占位（强行注入服务端不认识的键是无效探测）；
- **动态签名钩子**：`--payload-hook <py>`（flow/case_runner），模块暴露 `compute_envelope(action, business_params, personal) -> {信封键: 值}`——按最终业务参数现算签名（HMAC 等动态签名项目的适配点）。产出键必须 ⊆ 本轮信封注入键（越键报错：签名覆盖业务变异值是新的假缺陷源）；未配置 = 静态注入（personal_config 固定值，wjx 零变化）；钩子异常不吞、响亮失败。冒烟链路的 `--hooks` 是另一套业务适配层，两者独立。
- **冒烟 hooks 适配层受源码体检约束**：装载前先过 import 白名单（`json` / `time` / `__future__`）与危险能力黑名单（网络外发、进程、动态执行、任意文件读写、对象内省逃逸），命中即 `SystemExit` 点名文件与行号——`--hooks` 指向的文件此前直接 `exec_module`，被复制/转发的配置一旦被篡改就等于在测试机上任意执行。写钩子时不要 import 其它模块；节流用 `time.sleep`，数据解析用 `json`。

## M8 请求方法 / 请求格式 / 参数位置

接口不都是「POST + JSON body」。契约里能表达出来的形态，生成与执行会一路带下去；**表达不出来的一律按 POST + JSON + 全 body**（改造前行为，零变化）。

| 维度 | 认这些写法 | 落到哪 |
|---|---|---|
| **请求方法** | 「请求方式 / 请求方法 / 请求类型 / method」行、`GET /path` 示例行；OpenAPI 的 `paths.<p>.<method>`；JSON 契约的 `method` 字段 | `doc["method"]`；执行期 `call()` 用它发请求 |
| **请求格式** | `Content-Type:` 行、「请求格式：表单/json/xml/纯文本」行；OpenAPI `requestBody.content` | `body_kind`（`form`/`raw`）+ `content_type`；raw 还需 `raw_body_field` 指明哪个参数承载整包报文 |
| **参数位置** | ShowDoc 表格的「位置 / 传参方式 / 参数位置 / in」列（值支持 query/查询/URL 参数、header/请求头、path/路径参数、body/请求体）；OpenAPI 的 `in: query/header/path`；JSON 契约字段的 `location`/`in` | `request_fields[].location` → 产物 `param_locations`（数组）→ 执行期按名字分流到 URL / 请求头 / 路径模板 / 报文。path/header 位置只产「缺失」一种缺省态：path 段删不掉、header 上 null/空串与缺失发的是同一份请求（执行层按「不带这个头」处理），三态各判一次会把一个根因算成三次失败；`check_key` 分母同步不声明 `null_value` |

几条要点：

- **只写非默认值**。纯 POST + JSON + 全 body 的契约，产物里不会多出任何键——`cases_hash` 与回归基线哈希都按整份文档算，多写一个默认值键会让所有已批准套件与基线一次性失效。
- **path 参数不做报文变异**。URL 段落删不掉（删了就是另一条路由），所以 `B-MISS` / 空值四态 / 组合交叉都不围绕 path 字段生成，`check_key` 分母同步不声明这些约束——两边口径一致，不造「永远修不好」的假缺口。跳过原因写进 `mutation_skipped`。
- **header 参数不做 CRLF 载荷注入**。那是头注入而非接口校验；`security_payloads.json` 里含换行的载荷会被跳过并进 `payload_skipped`。
- **cookie 参数直接剔除并告警**。黑盒无法可靠伪造 Cookie 头，当成 body 字段发出去等于没测。
- **位置认不出就留痕**：表格里写了位置但值不认识（如「随便写」）→ 进 `parse_warnings` 点名，不按 body 静默处理。
- **query / header 正常参与校验**：它们的变异能真实改变报文，`B-MISS`、类型、长度、枚举都照常生成，分母也照常声明。
- **同名参数跨位置**（OpenAPI 里 `id` 既在 path 又在 body）：去重签名只取 `params`，会把两条折叠成一条，生成期 `gen_warnings` 会点名——遇到就人工拆开。
- **非 JSON 响应**：契约显式声明 `response_kind`（`text`/`xml`/`html`/`binary`）时才放行；放行条件是「正向用例 + 2xx + 形态合法（XML 必须能解析、不得是错误页）」，且计入浅用例。负向用例仍要求 `err_keywords` 字面命中响应文本，否则只到「待确认」——**默认仍是判「响应非JSON」失败**，不放宽。

## M9 生成期三类对账（都只报不挡）

生成完不等于覆盖够。以下三项解决「条数看起来合理、其实某块是空的」：

| 产物字段 | 对账什么 | 典型触发 |
|---|---|---|
| `plan_vs_actual` | `coverage_plan` 里每个**必测**维度的计划下限 vs **可执行**条数（TODO 占位 / `enabled=false` / `needs` 非空都不算） | 某必测维度 0 条可执行用例——占位也计入的话，「4 条全是要人工补的占位」会显示成已覆盖、`gaps=[]` |
| `priority_stats` | P0/P1/P2 计数与占比，附 `p0_probe`（P0 里有多少是机械探测） | P0 占比 ≥35%：wjx 的 P0 是「必测」不是「核心业务」，**不能用 P0 数量当业务覆盖证据** |
| `mutation_skipped` | 变异不成立而被跳过的字段 | `action` 这类走请求信封的字段不在 base params 里，删它是空操作，产出的用例与正常请求完全一致却期望失败 → 必然一条假缺陷 |

`NEEDS_CONFIRMATION` 归因不进缺陷台账，因此单独落盘 `pending_confirmations.json`：按维度分组、每组给出阻塞条数、`blocked_findings`、`resolution_condition`（确认哪个维度的哪类约束后放行）与 `impact`（组内含 P0 时升级为 `blocker`）。归因返回本身也带 `subject` / `resolution_condition`，不再只写一句 `confirm contract`。

同理，`ENV`（含「接口地址不支持此操作」这类 base_url / 网关不匹配）、`RATE_LIMIT`、`CONSISTENCY_PENDING` 三类归因只记「待确认」观察、不进缺陷台账——它们的共同点是失败原因不在接口本身，照单提缺陷会让开发白排查一轮；归因类别与建议动作写在描述里，翻案有据。`PRECONDITION_UNMET` 的匹配只在服务端**错误文案**（`errormsg`/`message`）里找 action 号，不拿整份响应做子串——响应回显 action 或 data 里带同号 id 都是常见巧合，命中一次就会把真缺陷判成前置。

## M10 业务场景补充（AF 维度族 · 默认参与，无真实场景则注明原因不参与）

自动生成走的是「字段 × 变异算子」的机械展开（`creater=12345`、空值四连、`title` 100+1 字符），
能保证**结构覆盖**，但产不出"用户实际怎么用"的业务场景——这类用例人类测试员根本不会写，
也发现不了业务逻辑问题。`AF` 维度族补的就是这一层：

| 子维度 | 含义 |
|---|---|
| `AF1` | 主业务流：典型用户操作路径 |
| `AF2` | 业务规则校验：业务语义上的合法性约束（**与 B 不重叠**——B 管技术参数校验，AF2 管业务规则，如"标题不得含品牌词"） |
| `AF3` | 业务组合场景：多字段组合产生的业务含义 |

三步走（`scripts/business_scenarios.py`）：`--prep` 出 prompt → LLM 生成 JSON →
`--save` 过门禁落盘 → `--merge` 并入主用例文件。**产物与 `case_schema.md` 完全一致，
不需要任何转换层，合并后 `case_runner` 直接可执行。**

`--prep` 出的 prompt 会自动附带从 L5 知识库检索到的产品行为参考（页面路径、按钮名、
开关名、已上线功能口径），并明确声明**与契约冲突时一律以契约为准**、知识库没提的
不臆造——让业务场景对齐真实产品而不是凭字段名想象。检索失败或知识库不可用时
自动降级为纯契约 prompt，主流程不受影响。

prompt 还会带上**业务流程位置**：按契约的 `action` 从 `assets/business_flow.*.json`
（带审批与 evidence 的流程知识）反查本接口出现在哪些流程步骤里，并**沿 `requires`
反向展开上游链**，同时给出状态约束原文。同一 action 对应多个步骤时全部保留并标注
`operation`（`1000102` 在流程里同时是发布 / 暂停 / 删除），不做猜测性收敛；未确定的
占位符 action（如 `<delete-response-action-not-found>`）一律排除。

配套一条**可执行性护栏**：依赖"上游已构造状态"才能成立的场景，prompt 明确禁止生成
本接口的 `success=false` 用例——本接口无法自证该状态，实际执行时状态不成立、接口正常
成功，期望拒绝却成功就会被判成 P0 假缺陷。这类场景写进用例 `note`，并在产物
`flow_constraints` 里留痕，说明"为什么没生成某类场景"。注入是增量：没有匹配到流程时
prompt 与未接入前完全一致。

```bash
python scripts/business_scenarios.py --contract <契约路径> --prep --out prompt.md
python scripts/business_scenarios.py --contract <契约路径> --save --agent-output <LLM产出.json> --out af_cases.json
python scripts/business_scenarios.py --merge --from af_cases.json --into generated_cases.json
```

**门禁**：底座是 wjx 自带三层（覆盖率 / 浅用例 / 空转，由 `case_runner` 执行），AF 另有七项——

- 借自 req2testcase 三项：数量纪律（条数必须等于 `expected_case_count`，不多不少）、占位符检测（"验证操作结果""功能正常"这类空洞短语直接 reject）、去重率 >50% 拒绝接受；
- C7.1 改造一项：契约实体覆盖——实体来源从"需求文本"换成**契约解析出的字段名与枚举**，覆盖不足只告警不阻断；
- 结构化用例专用两项：`dimension` 必须属于 AF1/AF2/AF3；`success=false` 的用例必须给 `err_keywords`；
- 族内覆盖留痕一项：`AF1/AF2/AF3` 缺族时记 `family_gaps` 并告警，**只留痕不阻断**。原因是不强制每族至少一条——BLOCK 会逼模型为过门禁编造场景，编出来通过校验后反而变成"已验证覆盖"，比缺口看得见更坏。判定交给覆盖率门禁：`--expect-categories AF1,AF2,AF3` 对账，不适用族用 `--exempt-categories` 写明理由。

**条数上限**默认 8 条（`WJX_AF_MAX_CASES` 可调）——业务场景每条都可能真实发请求，写接口会落数据，必须有硬上限。

**参与的判据是「有没有真实业务场景」**：`--af-cases` 给了才进 `coverage_plan`，用例直接
并入（来源 `business_scenario`，形状由 `business_scenarios.normalize` 单一来源保证，
不手抄映射）；没给就如实转不参与，`na_proofs` 写明「本轮没有真实业务场景可用
（未提交 af_cases.json）」并指出缺的是哪份输入。

**不用机械拼的合法请求充数**：那种用例只能证明「字段能发」，证明不了「用户实际怎么用」。
此前主链曾产出 `AF1/AF2/AF3-BASE-01` 三条 `af:mechanical_baseline` 基线，看着 AF 有覆盖，
实际契约没写枚举时 AF2 与 AF1 是同一份请求、AF3 只是删了非必填字段——一个维度算两次
覆盖，是典型假覆盖。现在这类基线整段移除，AF 要么有真场景、要么不参与，没有中间态。

`--af-cases` 的形状错误（缺 `cases` 数组、不是数组、空数组、归一化失败）必须出声：
静默当成「没提供」会让「交了材料却没生效」和「压根没交」在产物上长得一样。族匹配由
`case_coverage.dim_matches` 单一入口负责，`api_test_runner.coverage_gate()` 与
`case_generator.plan_reconcile()` 都按族认领，`A` 不会被 `AB` 前缀冒充覆盖。
只有显式 `--exclude-dims AF` 才是强制关闭（给了场景也不参与，N/A 证明留痕「显式关闭」）。

## M11 语义层接入（可选 · 让大模型读契约，不让它逐条写用例）

规则抽取（`field_semantics.py` 的字段语义标签）能稳定拿下**结构化约束**——长度、枚举、禁用词、默认值，
零成本且可复现。但它读不出业务语义：契约白纸黑字写着"子账户必须有系统管理员或问卷管理员权限"，
规则看到的只是一个叫 `creater` 的字符串字段，越权矩阵只能靠硬编码 appid 去猜。

语义层补的就是这一层（`scripts/llm_semantics.py`）：

```bash
python scripts/llm_semantics.py --contract <契约路径> --mode prep --out facts_prompt.md   # 出提示词（自带可引用的原文摘录）
# 大模型按提示词产出事实 JSON
python scripts/llm_semantics.py --contract <契约路径> --mode merge --facts facts.json \
       --out contract_enriched.json --report verify.csv        # 校验后并入；--out 仅供审阅
python scripts/flow.py --contract <契约路径> --llm-facts facts.json --plan-only            # 生成用例时消费
```

**默认即严格语义，只有两种状态**：不加开关——**先比对、后生成**，没有可认领的事实时只出提纲并 **exit 4**（不生成用例），交完作业重跑**一模一样的命令**才生成（作业位置 `<契约目录>/llm_semantic_prep/facts_<契约名>_<action>.json`，重跑自动认领，`--llm-facts` 显式指定优先）；`--llm-semantics` 只是显式重申，效果相同；`--no-llm-facts` 是**唯一关闭入口**——不出提纲、不用事实、纯机械。**无人值守（定时/批量）不降级**：脚本没有等人输入的能力，缺作业一律停在 exit 4，绝不拿机械结果冒充已比对。`--cases` 执行已审套件时不重新生成，不做抽取与比对（stderr 点名）。被拒收的事实一律在 stderr 点名并进 `llm_verify_report.rejected`，不静默。

默认严格模式的四条边界（都是实测踩出来的）：① 「停下等作业」这一步不发请求，因此**不要求** `WJX_BASE_URL` / `appid` 等运行配置，否则 `--execute` 第一次会在拿到提纲前被 exit 2 拦死；② `WJX_LLM_FACTS` 环境变量本来就被生成侧认作事实来源，严格模式必须把它算作「已交作业」，否则已交作业仍被判没交；③ 显式 `--llm-facts` 指向不存在 / 不可解析 / 形状不对的文件时直接拒绝——严格模式不能「没比对就生成」；形状判据抽成 `case_generator.facts_shape_error()` **单一来源**，flow 预检与生成期共用，不在两处各抄一份；④ `--no-llm-facts` 必须连环境变量一起屏蔽，只把 CLI 路径置空会留下半开开关（声明纯机械、实际仍并入事实），故 `case_generator.generate()` 有显式的 `llm_enabled` 命名参数，由 `flow.py` 传入。

**`facts.json` 与 `contract_enriched.json` 是两种形状，不能互换**：前者是模型产出的事实
（顶层 `fields`/`relations`/`unknowns`），后者是 merge 输出的**合并后契约**（顶层
`request_fields`/`response_fields`）。把后者喂给 `--llm-facts` 时，`verify()` 会拿到空
`fields`——零事实并入、不报错、不出声，产物看着完整。形状守卫现在会直接拦下并指出该传哪种文件。
`--no-llm-facts` 是**完整关闭**：显式 `--llm-facts` 与 `WJX_LLM_FACTS` 都不再读取，
否则「声明纯机械、实际仍并入事实」会变成半开开关。

**比对不一致：回原文 + 交回智能体二次确认**：`collect_disputes()` 只挑**字段级**争议
（`BLOCKED` / `MISMATCH` / `SUSPECT_BASE`；关系与 `unknowns` 的结构性拒收没有机械侧的
值可比，仍按原规则丢弃并在校验报告点名）。每条争议用 `_excerpt_spans()` 回契约原文定位
字段名所在行与 evidence 所在行，上下各扩 2 行并合并连续区间，产出**未截断、带行号**的
原文整段；臆造字段找不到时退回参数表表头区，让人能确认「清单里确实没有它」。
`build_review_prompt()` 把「机器值 / 模型值 / 机器判定 / 原文整段」写成争议单，
`flow.py` 在生成前预检到争议就停下（**exit 5**），不生成用例。智能体四选一写复核结论后，
`apply_review()` 过五道守卫才采纳：① `facts_sha256` 与 `dispute_fingerprint()` 一致——
该指纹**同时锁住事实文件与契约原文**，改过作业**或换过契约**都必须重做复核，否则会拿
旧结论套新原文（实测改契约后旧 review 被采纳、直接出用例，争议单还是旧片段）；
② **每条争议都要有一条 decision**，漏答的字段被点名并整轮不采纳，不许只确认一条、
剩下的让机器单方面丢掉（实测两条争议只答一条时 exit 0 出了用例）；
③ 只准改本次争议字段，夹带非争议字段一律拒收；④ `correct_llm_value` 的 `evidence`
必须是**本条争议贴出的片段**的连续子串；⑤ 修订值能在该 evidence 中找到依据，且只能改
`REVIEW_EDITABLE_KEYS` 里的可比对约束。采纳后产出 `facts_reviewed_*.json`，
**再跑一遍完整 `verify()`** 才进生成——二次确认不是绕过机械校验的后门。有拒收或漏条
就在 stderr 点名、重出争议单并停在 exit 5，不生成用例。

超长契约 prep 自动按段落**分片**：原文超过 `--excerpt-limit` 时切成多片，每片生成独立提示词
（`facts_prompt_shard01.md`…），字段清单按「字段名出现在该片原文中」过滤，片内明示
「只对本片字段抽取」。每片交给大模型各产出一份事实 JSON 后，用 `--mode combine` 机械合并
（字段冲突保留先到并告警、unknowns 去重），再 `--mode merge` 做全套校验并入。

**为什么放在这一层而不是让大模型逐条生成用例**：事实层的错误**可以机械校验**——字段名不在契约里、
evidence 不是契约原文子串、数值与解析结果不符，全是字符串与集合运算，不需要模型也不需要人工；
用例层的错误要等执行才知道。把大模型放在能被校验的位置，它最大的弱点就被管住了。

**五条硬约束**：

- 每条事实必须带 `evidence`，且必须是契约原文的**连续子串**——不是子串直接 BLOCKED；
- 关系（`relations`）与字段同等严格：没有 evidence、或 evidence 不在原文里，同样 BLOCKED。
  关系是跨字段推断，字段名各自都合法，唯一能证明「两者确实有关」的就是原文；
- 字段名只能取自解析出的字段清单，臆造字段直接 BLOCKED；`alias_of` 必须指向清单里**真实存在**的字段，
  否则会产出一条针对不存在关系的等价性断言；
- 与解析结果不符的（长度漂移、枚举膨胀、必填性写反）整条丢弃，不做部分保留——半对半错的事实比没有更危险；
- 契约没说的一律进 `unknowns` 并标 `must_not_assert`，禁止猜测。猜出来的事实会变成假缺陷，比不写更糟。

**声称的值必须能在 evidence 里找到**。写了 `max_len=100`，原文里就该有 `100`；写了
`enum` 含 7，原文里就该有 7。找不到说明这个值是从字段名或行业惯例推出来的，采信它就会产出
契约里根本不存在的边界用例。这条对「契约没解析出该约束」的情形尤其关键：契约无值**不等于**
可以放行，**必须有据**才放行。

**校验结论分三态**，因为它们对应的可信度不同：

| 结论 | 含义 |
|---|---|
| `PASS_VERIFIED` | 至少一项约束与契约值**比对一致** |
| `PASS_UNVERIFIED` | 提交了可比对约束但契约无值，且该值 evidence 有据 → 放行但记账 |
| `PASS_EVIDENCE_ONLY` | **没有提交任何可机械比对的约束**，只校验了字段存在与 evidence 是原文子串 |
| `SUSPECT_BASE` | 与契约值不一致，但**契约那个值在该字段行内原文里找不到出处、模型值找得到** → 事实保留、契约值不覆盖 |

第三态不能省。只记两态时，那些只写了 `role` 而没提交任何可比对约束的字段会与「比对一致」同态——
一份典型契约里真带可比对约束的往往只有三五个字段，报告里的「核验通过 N 条」会被读成 N 项都验过值。
三态在 `--report` 与产物的 `llm_verify_report` 里分开列。

**机械解析也会抽错，冲突时先回原文核对**。解析结果是**基准**，不是真值——它错了不会被自己发现
（自检只查「没把握」的三类，查不出「抽出来一个确定但错的值」）。所以数值冲突时按该字段自己的
**行内原文**（说明列 + 备注列）判一次：契约值在行内找不到出处、而模型值找得到 → `SUSPECT_BASE`，
事实保留、契约值**不覆盖**（它仍驱动 B 维度边界用例，静默改写会连带冲掉黄金对比与契约哈希；
这个状态的价值是**让冲突可见**，不是自动纠错）。三种情形必须保守处理：

- 两边都在行内（实测真案例：说明列写「最长 50」、备注列写「长度上限 100」，解析器按 `remark`
  在前抽出 100）→ 原文本身不足以判定，保持原判并留痕，不替人决定哪一列算数；
- 两边都不在 → 保持原判；
- 非 ShowDoc 契约（OpenAPI 的长度来自 schema 的 `maxLength`，不在 `description` 里）→ 一律按原规则，
  行内核对只对表格契约成立。

核对用的是「这个数字在不在这一行」的**独立包含判据**（带数字边界，`100` 不命中 `1000`），
**不复用抽取正则**——机械值本来就是那个正则抽出来的，用它再搜一遍只会得到同一个值，等于让
疑似出错的解析器给自己作证。另外 evidence 是全文子串、但可能取自**别的字段**那段（前段证据
套后段字段，子串校验拦不住），所以 evidence 不在该字段行内时会在结论里加一句提示——只提示、
不改判定，模型常用概括句而非原句，强判会大面积误杀。

**机械值待核的字段，它的探针用例要降级判定**。`B-LEN-EDGE-<field>` / `B-MISS-<field>` 的
期望方向完全由机械抽出的 `max_len` / `required` 决定——机械值可疑时，这些用例的期望整体
反过来，「恰好 N 字符应成功」变成假失败、「缺失应被拒绝」把合法请求判成校验缺失，和真缺陷
在台账里长得一样。`verify()` 通过 `out_meta` 回填 `suspect_fields`（两类：基准可疑 + 原文
歧义），生成侧给该字段的探针用例标 `base_suspect`，执行期 `run()` / `assert_validation()`
读到标记就把「缺陷」改为「待确认」并带 `BASELINE_SUSPECT` 归因。

**「模型值无据、机械值有据」不进这个名单**——那是模型错，把它降级等于静默吞掉真缺陷。
这条有反向测试锁着（把名单放宽到这类会让它立刻变红）。同理，`_gt_fields` 里同名字段跨侧
出现时按**请求侧优先**：请求侧是我们要发出去的，长度/必填与生成用例直接相关；响应侧同名
覆盖会把请求侧约束抹成 `None`，模型提交的长度事实于是永远走「契约未解析出」分支，值比对
形同虚设（实测 `simple_contract` 的 title 就是这种形态）。

**校验拦不住的，报告必须说清楚**：evidence 校验只能证明「这段话在原文里」，证明不了
「这段话与它声称的约束有关」——`evidence="签名"` 配 `algorithm="unknown"` 照样通过。所以报告同时
给出 `fact_utilization`：哪些事实键真有消费方、哪些只是存档（`llm_implications`、`relative`、
`is_url` 等当前不驱动生成）。这类「抽取到了但没人读」的键不算兑现。

**验收要数产物里的语义事实施例，不能只看 `fact_utilization.consumed`**：消费表里
`constraints.max_len` / `constraints.enum` 写的是「仅交叉校验；不驱动生成」，`evidence` 写的是
「报告留痕，不驱动生成」，两者都不含「不消费」字样 → 被算作「有消费方」。于是模型只交一个长度
事实、没有任何用例用它，`consumed` 依然非空——这是典型的假通过。硬判据是产物里的
`llm_verify_report.fact_cases`（`source` 以 `llm_fact:` 开头且 `enabled` 不为 False 的用例数）
与 `fact_trace_cases`（`LLM-UNK-*` 这类不执行、只留痕的缺口）。同理，`plan.semanticMode` 的
`factsConsumed` 只表示「传了 `--llm-facts`」，传一个空文件它也是真——不能拿它当验收。

**摘录截断会自动分片**：契约超过 `--excerpt-limit`（默认 6000 字符）时，prep 不再截断丢弃，
而是按段落边界切成多片（见上）；单片模式下若被 `--excerpt-limit` 截断，提示词会写明
「摘录已截断、覆盖到第几字符」，要求模型把摘录区外的字段放进 `unknowns` 而不是凭字段名推断——
截断区外没有可校验的 evidence。

**降级**：不传 `--llm-facts` 时纯规则链路照常工作，行为与接入前完全一致——接入是增量不是替换。
接入失败（文件不可读、JSON 损坏、顶层不是对象）时**降级并出声**，不静默当作「这次没接」；
模型把 JSON 包在 ```json 代码块里或前后加了解释，会被自动提取，不白丢一次抽取结果。

**抽取稳定性可度量**：`--mode compare` 对同一契约的**两份**抽取结果做关键事实比对
（role / max_len / enum / alias_of / required / 关系集合 / unknowns 集合），报告一致率与分歧清单，
`confidence=explicit` 的分歧单独标出——explicit 层的分歧比 inferred 层严重，应优先人工复核。
一致性高不代表事实正确（两次一致地错仍可能，正确性靠 merge 的机械校验）；一致性低则说明
该契约的事实抽取不可靠，驱动硬断言的事实需人工复核后再用。

**并入与兑付是两件事**：并入由 `llm_semantics.py` 负责（回答「有没有」），兑付成用例由
`scripts/llm_fact_cases.py` 负责（回答「用不用」）。分开是为了能单独度量兑付率——事实并进了
却没人消费，表面上"接好了"实际没兑现，是最容易自欺的一环。

并入后字段上带 `llm_role` / `llm_constraints` / `llm_evidence`；契约级带 `llm_relations` /
`llm_unknowns`。并入采用**整体替换**语义：本次没有事实的字段会清掉上一轮残留，避免同一契约
被并入两次后留下「新关系 + 旧字段事实」的混合态。各类事实的兑付方式：

| 事实 | 兑付成 |
|---|---|
| 权限约束（如子账号需某角色） | 越权矩阵多出 `A08`「无权限子账号应被拒绝」——规则层看着字段名做不出来 |
| `fallback_chain` 取值兜底链 | 目标字段未传时的取值来源与默认值用例；relation 级与字段级两种表达，同一对字段只兑付一次 |
| `alias` 兼容别名 | 只走别名 / 只走主字段两条路径。方向由 verify 机械判定（role=alias 的一侧、或 `alias_of` 互证），判不出转 unknowns 留痕——**不按 between 数组顺序猜**；判明方向后若字段没写 `alias_of`，merge 兜底回填 |
| `forbid` 禁用词 | 传入禁用词应被拒绝（仅 evidence 里真有该词的；惯例推的词不兑付） |
| `default` 默认值 | 字段未传应落到声明默认值（仅 evidence 有据；回读比对落值与文档是否漂移） |
| `publish_flag` 开关字段 | 契约声明的默认值自动断言；另一取值契约未说可否显式传入 → 只留痕 |
| 状态字段枚举在契约外 | 留痕点名，禁止编造枚举值去断言状态流转 |
| `url_compose` 域名 + 相对路径 | 留痕给拼接公式；两个字段都不是绝对 URL，单字段断言必误报 |
| 语义角色（`llm_role`） | 字段名猜不出 token 时照样激活业务域维度，见下 |

业务域维度（N/Q/W/S/T/O/P/R/U）默认按字段名 token 命中。`dim_generators.ROLE_DIM_MAP` 补了
第二条命中口径：**字段名不含 token、但语义层把某个请求字段判成了等价角色**（如 `creater` 判为
`operator_identity`）时照样激活。映射表刻意开得很小，宁可少映射——映射过宽会让维度在无关接口上
被激活。语义激活的用例 `source` 带 `(llm_role)` 标记、note 里写明契约依据，因为契约未必明说
服务端会校验该引用，这类断言比 token 直接命中弱一档。只认请求字段：响应侧字段无法构造请求。

兑付层同样守 must_not_assert：契约没说的只生成 `needs=manual` 留痕，不做自动断言；推断出的
关系（`confidence=inferred`）在 note 里标明是推断，不引作契约原文。校验结果随产物落盘可审计。

## M12 资产归档与正式化（默认安全路径）

生成与执行的资产默认不散落在当前工作目录根部，而是由 `scripts/asset_runtime.py` 统一归档到包外子目录：
`<cwd>/api-tests/<project>/runs/<interface>/<可选version>/<unique>/`。设置
`WJX_API_TEST_ASSET_ROOT` 可替换根目录；`--project` 默认为 `WJX_PROJECT_NAME` 或当前目录名，
`--version` 可选。接口标识优先使用 `action-<action>`；没有 action 时使用 REST 的
`<METHOD>-<path>-<hash>`，因此同一路径的 GET 与 POST 不会混为一份资产。

`flow.py`、`case_generator.py` 共用上述归档规则。传 `--out-dir`/`--out` 时，目标必须是新建或空目录（
`case_generator.py --out` 是显式新文件，文件已存在即拒绝），禁止覆盖历史产物。`flow.py --out-prefix`
只改变报告文件名前缀，**不提供全量产物隔离**，也不能替代新的运行目录；`case_runner.py`、
`smoke_runner.py` 等低层入口不自动接入这套归档，仍按各自参数写出。

每个 flow 运行目录至少包含 `generated_cases.json`、`plan.md`、`run_manifest.json`；真实执行另写
`executed_cases.json`，并在 `run_manifest.json` 的 `status`/`selection`/`results`/`artifacts` 中记录计划、选择范围、执行结果和产物。
状态 `planned` 只表示已生成或计划/dry-run，`running` 表示正在执行；`completed` 表示本轮声明的范围已完整跑完且全通过；
`partial` 表示有意只跑了一部分（`max_cases` 截断、`smoke` 等档位收窄），执行本身干净但**不构成全量验收**；
`failed` 表示存在失败、覆盖缺口、回读错误或执行不完整。计划模式不得冒充完成。

`--only` 是用户声明范围：覆盖率分母收窄到所选维度，被排除的维度写入 `inputs.coverage_excluded` 留痕，
不计为已覆盖也不判缺口。先应用 `--only` 声明范围，再应用档位和 `max_cases`；范围外禁用或低优先级用例不影响完整性，只有声明范围内被档位或限额排除才判 `partial`。

**生成与执行分离**：`flow.py --contract ...` 负责生成，审阅后用
`flow.py --cases <已保存用例.json> --execute --out-dir <新空目录>` 执行，`--cases` 不会重新生成也不修改源文件。
因此不要把“先 flow 计划、再 flow execute”当成复用计划的方式；后一步若仍传契约会重新生成。

**批准正式用例**：`--approve-cases <src> --approve-by <人> [--suite-out <target>]` 是显式动作。
默认另存到 `<资产根>/<project>/suites/<interface>/<suite>/<hash>/cases.json`；传 `--suite-out` 可指定新文件，始终不改源。批准会拒绝空套件、重复/空编号、
TODO/人工待补、禁用用例、未知/人工/非字符串检查器、缺少用例自身 `action`/`name`/`dimension`/`params` 的不可执行用例和真实凭据（包括 JSON 头文本、URL 编码凭据键与 userinfo），并写入 canonical `cases_hash` 与批准人/时间。
执行快照不继承套件的 `approval`：`executed_cases.json` 用 `source_approval`/`source_cases_hash` 记录来源，
因此已批准套件按 `--only`/档位筛选执行不会触发“内容已变化”。

**回归快照与正式基线**：真实执行后在本轮目录生成 `regression_baseline.json`，它是带
`snapshot: true` 的未批准快照，不等于正式基线。`--retest <snapshot-or-baseline>` 读取历史基线，
且快照必须位于本轮输出目录之外；复测结果写入 `retest_verdicts.json`。每条 entry 的 `case_hash` 绑定完整用例内容；加载时从历史 `cases` 推导并核对，当前参数/预期/检查器等内容变化判 `STALE_BASELINE`。旧基线无完整内容证明时，统一 flow 复测判 `UNBASELINED`，不得仅因本轮 PASS 判 `FIXED`。只有
`--promote-baseline <snapshot> <target> --approve-by <人>`，并且快照逐条实际执行、全部 PASS、无覆盖缺口时，
才会另存为正式基线；还须保留源运行目录，核验真实 `source_run/run_manifest.json` 为 completed、无 findings，
快照内容与该目录 `executed_cases.json` 逐字节同源（canonical 哈希一致），且条目契约哈希与本次运行契约一致、期望与用例一致。禁止原地覆盖快照。

**多接口 acceptance manifest**：`scripts/multi_interface.py --manifest acceptance.json --out-dir <新空目录>`
默认只预检并生成各接口计划；只有显式 `--execute` 才把真实执行传给子 flow。manifest 顶层使用
`mode: "acceptance"` 或 `"regression"`、`entries` 数组；每项至少有 `cases`（相对 manifest 的用例文件）和
`cases_hash`（去除 approval 后按 JSON canonical 序列化计算的固定 SHA-256），可选 `config`、`baseline`、`only`。
所有 entries 会先完成路径、JSON、哈希、重复引用、执行配置字段类型/枚举、`only` 命中性和基线预检，任一失败则不执行任何接口，并在汇总中标 `notRun`。
预检缓存已验证的原始字节；第一条请求前整体冻结全部 entries 到 `inputs/entry-###/{cases,config,baseline}.json`，按角色命名避免同 basename 覆盖。全批冻结后及每个子项开始前校验摘要，执行期源文件变化或消失不影响实际内容；冻结失败整批 `notRun` 且零请求，单项准备异常留该行原因并保留此前汇总。
每个接口使用独立 `run-###` 子目录，汇总 CSV 路径在发出任何请求前完成可写性校验；
最终输出 UTF-8 BOM 的 `multi_interface_summary.csv`（可用 `--out` 指定）。汇总状态来自实际 `run_manifest` 并核对子运行的实际内容哈希：
只有 `completed` 且全 PASS 才算通过，`partial`（截断/档位收窄）与 `notRun` 都不算验收通过，单个 entry 解析失败只标记该行，不中断整批。

## M13 计划审阅与依赖梳理（执行前先看一眼）

`flow.py` 除 `generated_cases.json` 外，默认多产两份计划，`--plan-only` 同样产出——那正是它最有用的场合：每轮都要付执行成本（写接口会落数据），跑完上百条再发现场景设计不对很浪费，先扫一页计划便宜得多。

| 产物 | 作用 |
|---|---|
| `plan.md` | 人可读计划，四段：用例总览 / 待确认问题 / 前置依赖与关系 / 风险与不适用凭据 |
| `dependencies.json` | 机器可读的显式跨接口依赖，含原文证据与行号；同时进 `intelligent_test_plan.json` 的 `dependencies` 字段 |

**依赖取数纪律**：只认契约正文**显式声明**的前置接口（如「请先调用修改问卷状态接口1000102，传入state=2」），**不做字段名相似性推断**；每条依赖必须带**契约原文连续子串**作证据；正文写了"要先调某接口"却给不出 action 号时进 `unknowns` 留痕，**不生成依赖、也不生成用例**——定不位就不调，猜错比不测更糟。契约没声明依赖时计划会写明"未显式声明"，并提示这**不等于本接口没有前置条件**。

**为什么不自动补全依赖**：契约很少写前置关系（实测 193 篇契约只有 1 篇显式声明）。相比按接口名猜出一条链，少一条依赖只是少测一个场景；猜错会调一个语义不符的接口，把"前置条件没满足"伪装成"已按依赖链验证"，比不测更糟。因此本能力**只提高召回下限，不承诺召回上限**。

依赖的原文证据同样进 `plan.md`，便于人工核对声明是否被正确理解。

### 运行实证通道（在测试中发现依赖）

契约常常不写前置关系，但**真实失败响应会写**。所以除读契约外，执行后还会就地筛一遍失败响应：
命中「请先调用 / 需先 / 前置条件」这类话术的失败被整理成抽取提示词，由大模型抽事实、
机械校验后成为**候选**依赖；人工确认后才转正式。

| 通道 | 来源 | 触发条件 | 何时过期 |
|---|---|---|---|
| 契约声明 | 契约正文白纸黑字 | 不需要执行 | 契约改了 |
| 运行实证 | 真实失败响应里的提示 | **必须先真的跑失败一次** | 接口行为改了 |

两条通道互补而不是替代：契约通道**保下限**（不写就没有，实测 193 篇只命中 1 篇），
运行通道**提上限**（用例没构造出前置场景就永远失败不了、也就发现不了）。
两条通道在统一入口 `flow.py` 的执行前**实际合并**（`merge_dependency_channels`）：
同一对「主体接口 / 目标接口」两条都命中时**以运行实证优先**——真实证据强于文档声明；
只有运行实证一条参与时行为与合并前一致。注意只有 `kind=depends_on`（「请先调用 X」
这类前置语义）的契约条目参与判定，`companion_read`（配套读接口）不是前置条件，
参与判定会把「失败归因到配套接口」整类误判。

**确认这道闸对两条通道的宽严不同**：运行实证通道必须人工 `--confirm`（候选不参与判定）；
契约声明通道**不需要人工确认**即可参与——它不是从错误文案里猜出来的，而是契约正文
白纸黑字写出的，没有「猜错吞缺陷」的风险面。命中后该用例的状态改为 `PRECONDITION_UNMET`，**既不算失败也不算通过**，
在报告里单列点名，且**不进缺陷台账**（记 observation 而非 issue）。也就是说它会让一条失败
从缺陷台账里消失——判错的代价是一个真缺陷被静默吞掉、外观还完全合理。因此候选依赖
一律不参与判定，只有 `confirmed` 才生效，跨主体也不误吞（`attribution_engine` 对此有硬校验）。
没有运行实证记录时，行为与接入前完全一致。

**执行前自动就位依赖契约**：加载到 confirmed 依赖后，执行前按 `target_action` 解析目标接口
契约并落盘 `runtime_dep_contracts.json`——先在**主契约同级目录**找（"契约集放一起"是推荐用法，
本地命中就不查库），再按 action 从知识库定位，每条记 `origin`（local/kb）；都取不到的进
`missing` 点名留痕。Agent 构造前置请求时直接用清单里的路径，不必再手动 `kb_load_contract`；
缺契约的依赖按「缺料点名」处理，不猜不伪造、不阻断执行。
