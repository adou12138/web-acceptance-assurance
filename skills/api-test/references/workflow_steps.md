# 七步深度流程细则

> `SKILL.md` 只留路径判定与红线；每步骨架与完整口径在本文件，编排顺序另见 `playbooks/seven_step.md`。
> **执行到某一步时打开对应小节**，不要通读全篇。

## 第 0 步：登记当前指定的环境

只登记**用户当前要测的那一个环境**：从接口文档『接口地址』取 **BaseURL（禁止写死默认域名）**、路径、encode、appid、sign（是否校验）、主/子账号，写入 `references/env_config.md`（多域名指向同一后端时合并记录）。**地址经 `WJX_BASE_URL` 传入、不写死进脚本**。

## 第 0.5 步：从知识库载入接口契约（可选，推荐）

> `scripts/kb_load_contract.py` 扫描知识库 `project/` 下的 `.md/.json/.yaml/.yml` 契约文件（`project` 不存在时退回知识库根），ShowDoc markdown、OpenAPI/Swagger、极简 JSON 契约放在任意子目录都能按文件名命中。Confluence 等需登录来源仍需粘贴契约文档。

`python scripts/kb_load_contract.py --kb <KB_ROOT> --action 1000107`（或 `--keyword "AI主页"`；`--out contract.md` 落盘）。

- **`--out` 命中多页时默认拒绝写出**（退出码 2 并列出全部候选）——多页合并成的文件在下游看来就是「一个接口的契约」，各页字段会揉进同一份字段集，第二个接口的字段从此成为第一个接口的断言前提，执行期只表现为「字段缺失」假缺陷；确需多页通读时显式加 `--allow-merge`，该文件仅供人读、**不可作为单契约输入**。
- **`--kb` 可省略**时按 `KB_PATH` 回退（剥离适配：本包内无同级 `qa-req2testcase-generator/user_knowledge`，该回退必失败——请显式传 `--kb` 或设 `KB_PATH`）。
- **加 `--endpoint`** 从契约「接口地址」字段自动抽出真实 URL（打印 `ENDPOINT: <url>`），第 5 步的 `WJX_BASE_URL` 必须用它。
- **匹配策略**：先按文件名 `[1000107]` 精确匹配，再用 `_vector_index/meta.json` 兜底模糊检索（纯标准库）；检索为空则回退"用户粘贴契约"。

## 第 1 步：梳理接口契约

提取动作 / 路径 / 方法、必填与可选参数、类型、枚举取值、长度/数值边界、响应结构（成功 data 字段、失败 result/errormsg），写入 `references/framework.md` §9.1 接口信息表模板。标清鉴权模型（签名/Token/AppID/子账号）与状态机（创建→发布→暂停→更新→删除）。

## 第 1 步（审查模式变体）：接口文档合理性审查

> 当用户意图是「审查 / 校验接口文档是否合理」而非「执行接口测试」时，**进入文档审查模式：不发起真实调用，只审文档原文**。结论复用 31 维度框架，问题记入文档审查台账（统一 16 列，列定义以 `references/issue_format.md` 为唯一来源，与执行侧同源；详见 `references/doc_review.md`），并与后续测试衔接。

审查六个面（每面的展开判据见 `references/doc_review.md`）：

1. **字段参数说明**：名称 K7 / 类型 B,K / 必填 B1 / 取值范围 B2,B3 / 默认值 B9 / 单位 K / 示例 K9,B 是否齐备准确。
2. **前后一致性**：请求↔响应字段名、多处描述、跨接口命名风格 K7、向前兼容 L2。
3. **错误码与错误信息**：完整性、码↔文案映射 H9、HTTP 状态码与业务码区分、根因不掩盖 H6、未声明码。
4. **边界条件**：空值 / 超长 / 越界 / 特殊字符、分页 AA、并发、时间边界。
5. **字段间依赖关系**：条件必填、互斥、联动、组合约束——未说明即记「依赖关系缺失」，高优先级。
6. **歧义 / 缺失 / 不合理**：模糊措辞、空白项、示例与说明冲突。

输出 `api_test_doc_review_report.md` + `api_test_doc_issues.csv`（**均为纯人工交付物，无脚本生成**；产物放置位置与 exit 3 前置门禁的查找顺序以 `references/doc_review.md` §4 为唯一出处）。**纯文档缺陷**反馈文档 owner；**文档与实现不一致**记「需求确认」转测试并作为后续优先验证项。四种契约来源与维度映射见 `references/doc_review.md`。

## 第 1.5 步：接口适用性判断（必做，决定哪些维度适用）

加载 `references/applicability_matrix.md`，按五步法判断：① 识别业务域 → ② 识别操作类型（查询/创建/修改/删除/导出/导入/订阅/配置）→ ③ **判断是否国际版场景** → ④ 从 §4 矩阵筛选适用维度 → ⑤ 不支持的功能标注 **N/A**（不计入通过率，但必须列出证明已判断）。

> **核心原则**：不是每个接口都支持所有功能——创建资源接口不适用"导出下载"（M），查询接口不适用"状态机"（E）；强行套用只会产生误报。操作类型对应表见 §1，反例见 §2，N/A 规范见 §3，**国际版判定见 §0（默认国内版，国际版维度全部标 N/A）**。
>
> **易漏提醒**：**AB（前端-接口口径一致性）不体现在操作类型里**——只要接口在前端有对应操作就必须测，纯接口视角测不出前后端不一致（历史缺陷占比约 8.4%，第二高发）。测 AB 前先拿**页面基线**（人工页面操作 / 浏览器自动化抓取 / 设计稿三选一），无基线的 AB 项只能记缺口，**不得凭空填预期值**。

## 第 2 步：按 31 维度设计覆盖（A–L 通用 + M–Z 业务域专项 + AA–AE 通用补充）

加载 `references/framework.md`，把接口套入 31 大类，逐类判定覆盖状态（强/部分/缺口/排除/**N/A**），用 §4 覆盖率矩阵记录。

- **M–Z 专项**只在接口属于对应业务域时测（第 1.5 步判断）。
- **AA–AE 补充按接口形态判定**：AA 分页（列表接口必测）、AB 前端口径（有页面的接口必测）、AC 幂等唯一性（写接口必测）、AD 事件回调（按接口形态由适用性矩阵判为**选测**，不进硬门禁——见 `applicability.OP_MATRIX`）、AE 认证/传输补充（认证生命周期、请求头与传输契约、mTLS、重放时间窗；`applicability.py` 六种操作类型的必测元组均含 AE，不适用时的默认理由见其 `NA_REASON["AE"]`）。
- **国际版维度默认全部标 N/A**；AF 为业务场景维度族，不计入上述 31 类，启用规则与条数上限见「机制速查」M10。
- **优先补齐"假通过"与"假失败"两类盲区**：C 字段语义真值（更新后回读）、E 状态机、H 错误语义具体性（含 H6 根因不掩盖）、G 安全（含内容安全）、**B8 过度校验（合法输入被误拒）**。
- 用例用 §3 三要素模板描述（输入要点 / 观测点 / 预期行为 / 优先级 / 依赖环境 / 可自动化）。

## 第 2.5 步：过一遍高频缺陷模式清单

加载 `references/defect_patterns.md`，按完整 21 条缺陷模式（12 条 Top + 9 条补充）逐条确认是否可能命中，命中的转成用例挂到对应维度下——补齐"框架想到了、但没想到具体怎么坏"的盲区。**回归复测时改过「回归复测专项」**：先对照三类套件自误报陷阱（过期期望 / 空转假通过 / 硬编码 finding）。

## 第 3 步：收紧断言 + 辅助验证（最关键，决定能否测出问题）

**断言分层——先定判据，再跑用例**：

| 层 | 要断言什么 | 不做会怎样 |
|---|---|---|
| **拒绝层** | 异常用例必须命中**文档化的错误关键词**（`err_exact`） | 未配 `err_exact` 的用例即使被拒绝也判「待确认（高危）」而非 PASS——拒绝原因可能是未登录/缺参数而非目标校验生效；配了却未命中判 FAIL |
| **成功层** | 响应 **data 契约字段与类型**，不只看 `result=true` | 假通过 |
| **状态层** | 所有请求校验 **HTTP 状态码**：5xx 一律记问题（即使业务"正常"）；4xx 需校验状态码语义（400/401/403/404/409/429）与业务错误码一致（§9.7） | **401（未认证）与 403（越权）混用即为缺陷**被放过 |
| **反向层** | **过度校验**：文档标注为可选/可空的字段，传 `null`/空串/不传 → **应成功**，被拒即记缺陷 | 最高发触发点是"读接口返回的结构直接回写给写接口"，用 `assert_no_over_validation()`，见陷阱 14 |

**辅助验证（核心能力）**：创建/修改/删除/状态变更后，调**独立**查询/列表/统计接口交叉验证（矩阵见 §9.4.2）——创建后验详情字段一致 + 列表出现 + 计数 +1；修改后验字段生效且未传字段保留原值；删除后验详情不存在 + 列表消失 + 计数 -1；状态变更后验详情状态字段 + 公开访问接口生效；导出后验下载链接可访问；批量操作后验成功项生效、失败项不变。三层次：存在性 → 字段一致性 → 副作用完整性，**至少做到第 2 层**；辅助接口失败先归因（环境/同步延迟/权限/真实缺陷，见 §9.4.4），不直接判主接口缺陷。helper：`verify_by_query()` / `verify_by_list()` / `verify_absent()` / `verify_count_delta()` / `chain_verify()`。

**按维度选用断言 helper**（`framework.md` §2 场景族末尾标注，适用维度必选对应 helper）：AA `check_pagination()`、AB `check_ui_parity()`（`page_value` 来自页面基线登记表，禁止凭空填）、AC `check_uniqueness()`、AD `check_event_delivery()`、AE `check_transport_contract()`（请求头与传输契约、认证生命周期；AE 为全操作类型必测，不得因文档未写而跳过）、H9 `check_error_code_mapping()`、命名 `check_field_naming()`、国际化 `check_error_i18n()` / `check_currency()` / `check_datetime_tz()`（后两者仅国际版）、HTTP 语义 `check_http_semantics()`。

**连接/网络异常**自动重试（次数由 `RETRY_COUNT` 控制），重试后仍失败归 **ENV/网络问题**，不计入业务缺陷。

## 第 4 步：问题记录（CSV，现象化）

按 `references/issue_format.md` 的**统一 16 列**记录（基础 9 列 + 证据链 7 列：置信度 / HTTP状态码 / 请求ID / TraceID / 证据路径 / 归因 / 复测状态）。**维度列填触发该问题的维度编号**（如 `B8`/`AA3`/`H9`），便于按维度统计缺陷产出、反哺高频模式清单。描述用**现象口吻**（"写了脚本也能保存"而非"未做 XSS 过滤"）。安全拦截类记「符合预期」，二者都**不是缺陷**；仅在确实做了多环境对比且观察到差异时，才记「环境风险(ENV)」。runner 自动导出 `api_test_issues.csv`（utf-8-sig 逗号分隔，Excel 不空白）。

> **铁律——请求 Body 必须含公共参数**：问题单「请求Body」列记录**真实完整报文**，必须含 `encode`/`appid`/`action`/`sign`/`ts`（正/反例见 `issue_format.md`），开发要能原样复现。运行器 `add_finding()` 已对含 `action` 的报文自动补齐；**独立脚本必须自行补齐**（可调用运行器导出的 `complete_request_body()`），否则就是不完整台账（陷阱 18）。

## 第 5 步：在指定环境执行

在 runner `main()` 编写用例（参考现有示例骨架：创建→更新→异常→安全→鉴权），运行 `python scripts/api_test_runner.py`。**测试地址从契约的实际『接口地址』取**，用环境变量传入：`WJX_BASE_URL=https://实际地址/实际路径 python scripts/api_test_runner.py`。runner 不内置任何默认域名或路径。**只在当前指定环境跑**；与"指定环境"无关的环境性异常（连接失败、限流）先归 ENV/网络问题、重试隔离，不计入业务缺陷。

## 第 6 步：复盘、收敛结论与数据清理

1. 核对"是否还有假通过/假失败盲区"（§6 清单，含过度校验与前后端一致性）。
2. 待确认项逐条给结论（缺陷 / 符合预期 / 已确认非问题 / ENV）。
3. 输出回归报告（用例数 / 通过 / 失败 / 问题数）。
4. **清理测试数据**（§11 规范）：统一前缀 `TEST_AUTO_<用例号>_<随机串>`、工厂函数构造前置数据、`try/finally` 中调 `teardown()`（另有崩溃安全的 `register_cleanup()` / `run_cleanup_manifest()` / `--cleanup-only`）、每轮按前缀扫描孤儿残留、并发线程各用独立资源**禁止共享同一 ID**（否则产生"数据串了"的假缺陷）、不可删资源记入"环境残留清单"。

统一 flow 清理另行要求 `environment.type=test`、`write_enabled=true` 与显式清理开关；仅登记并删除 action 与套件一致、明确创建/新增且带本轮 run_id/case_id 所有权的资源。查询/修改返回既有 ID 不产生所有权，外轮资源不得删除。

**警惕两类误判**：把"被正确拦截"当缺陷；被防重提交/限流污染成"不稳定误拦"（复测时正文加随机串 + 间隔 ≥0.4s 绕过）。

## 冒烟模式的完整口径

> 用户要「把一批 / 全部接口跑一遍，看哪些通」时**走冒烟模式**，不套七步深度流程。分工、案例字段、判定规则、清理授权见 `references/smoke_testing.md`。

**执行三步**：

1. 备齐三份资产——`--config` 环境配置（地址模板 / 公共参数 / 账号 / QPS 档位 / 判定关键词）、`--cases` 案例清单（按**依赖顺序**排列）、`--hooks` 业务适配层（可选，只放无法用数据表达的动作）。
2. 先空跑再实跑——`--dry-run` 确认参数渲染无异常 → `--only <单个action>` 试连通性 → 再全量。
3. `python scripts/smoke_runner.py --config <cfg> --cases <cases> [--hooks <hooks>] --out-dir reports`。问卷星 48 接口可直接复用 `assets/` 下参考实例。

**判定四级**：PASS / FAIL / N/A（环境限制）/ ERROR（网络异常），**服务端 5xx 一律判 FAIL**，不会被 N/A 关键词吞掉；HTTP 200 里的服务端内部错误（内部错误 / 系统错误 / traceback 等）优先于 `na_keywords` 判定。FAIL 与 ERROR 进问题台账（统一 16 列、走统一归因——环境 / 限流归"环境风险"类、其余记"缺陷"，并自动写**脱敏**证据包）；N/A 单独列清单不计缺陷，但会补一条「待确认/低」的留痕行，所以**台账行数 ≠ 缺陷数**。

**产物**：结果 CSV（**真实完整请求报文**含公共参数 + 响应报文各一列）、问题 CSV、report JSON、summary MD。report JSON 与 summary 另带**延迟分布**（P50/P95/最大值/均值 + 离群提示，排除 N/A 与 dry-run 的 0ms）——只作参考与离群提示，**不参与判定、不进问题台账**：单轮单次耗时含网络抖动，不是性能基准；它也**不改变 J 维度（性能与并发稳定性）的适用性判定**，J 仍是选测项、没有阈值断言。

**反哺**：`--feedback` 可把本轮「缺陷」回流为模式候选（进 `references/pattern_candidates.log.md` 待评审池——运行时数据、已 gitignore 不入库；纪律与登记口径见 `references/pattern_candidates.md`）。

**脱敏口径（深度链路与冒烟同一条纪律）**：深度链路产物（`api_test_issues.csv` 台账「请求Body」列、`api_test_report_full.json` 的 `findings[].request` 与顶层 `fixed_params.sign`）同样默认脱敏——`sign` 等凭据类值打码为 `***`、键名与结构保留，开发凭手上配置即可复现；仅内部调试可用 `WJX_NO_REDACT=1` 关闭（关闭时启动即警告），外发报告不得关闭。冒烟的对应开关是 `--no-redact` / `WJX_NO_REDACT`。

**衔接**：冒烟圈出的 FAIL 项转七步深度流程定位根因；冒烟不做深度断言，深度流程不做批量探活，两者不互相替代。

**清理纪律**：**适配层的收尾清理默认不执行删除**——`assets/smoke_hooks_wjx.py（站点专属钩子，未随本包分发）:95` 判 `teardown_enabled`，默认 `false` 时只列出待清理清单、不删数据；配置 `true` 后才真正删，且只清理本次运行登记的资源，开启前必须确认目标为测试环境。**注意这只约束"收尾清理"**：案例清单里显式的删除类案例仍会照常执行，删除前必须先取得授权（见 `SKILL.md` §2 执行前确认检查点）。
